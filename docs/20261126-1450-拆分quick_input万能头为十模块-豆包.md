# 拆分 quick_input.h 万能头为十个模块（v0.9.178）

> 撰写：2026-11-26 14:50，豆包。对应提交 v0.9.178。
> 前置文档：[20261124-1346-项目现状分析与问题清单-豆包.md](20261124-1346-项目现状分析与问题清单-豆包.md) 的 P1-6「架构膨胀」。

## 1. 为什么拆

`cpp/quick_input.h` 从 v0.9.3 的 5267 行涨到 **6991 行**，同时装着 v 模式符号表、日期、计算器、数字转中文、货币、单位换算、u 模式笔画、Tab 补全、i 模式短语、联想、繁简转换、拼音分词、用户词频、皮肤、云拼音、模糊音、剪贴板、长句切分、输入统计、纠错、候选打分、DP 分词、表情面板、云 provider、跨设备同步、候选窗 GUI、以及 v0.9.164–v0.9.167 的"增强入口"链条。

后果有三个，都是实际遇到的：

1. **定位成本**：报错行号落在 6991 行的文件里，任何一次编译错误都要先翻几百行找上下文。
2. **重复实现**：CLI 和 addon 各自抄一份逻辑（英文判定"双写辅音"在 CLI 出现 3 处、addon 1 处），因为头里没有清晰的边界可复用。
3. **不敢改**：所有功能挤在一个 TU 里，任何一处改动都可能牵动别处，没人愿意动这个文件——于是它只会更大。

## 2. 方案：片段头（fragment header），不是独立模块

拆法有两种，这次选的是风险最低的一种：

| 方案 | 做法 | 风险 |
| --- | --- | --- |
| 独立模块头 | 每个头自带 `#pragma once`、include、`namespace pinyin_ime { ... }`，CLI/addon 改成按需 include | 需要改调用方 include 列表；跨片段依赖（`stats` 依赖 `CloudCandidate`）会让 include 顺序变得敏感 |
| **片段头（本轮采用）** | 片段只装声明，**不带 namespace 也不带 include**，由 `quick_input.h` 在 `namespace pinyin_ime` 内部按原顺序 include | 调用方零改动；预处理后 token 流与原文件完全相同 |

选择片段头的理由是"语义零变化 + 调用方零改动"，这样 addon（本轮环境编译不了 fcitx5）也能保证行为不变——因为 token 流没变，编译器看到的东西一模一样。

## 4. 踩的坑：namespace 会嵌套

第一次拆的时候给每个片段都加了 `namespace pinyin_ime { ... }`，而 `quick_input.h` 本身已经开着 `namespace pinyin_ime`，于是片段里的声明落进了 `pinyin_ime::pinyin_ime`，报错是这种形态：

```
error: ‘quick_candidates_v5’ was not declared in this scope;
did you mean ‘pinyin_ime::pinyin_ime::quick_candidates_v5’?
```

`namespace A { namespace A { ... } }` 在 C++ 里是**嵌套**，不是重开同名 namespace——和 `namespace A::A` 等价。片段头因此定为"不带 namespace"，并写进 CI 守卫，防止以后有人"好心"补回去。

另外把 `#include <string>` 之类放进片段也是错的：片段被 include 在 namespace 内部，标准库头会在 namespace 里展开，直接把 `std::` 污染成 `pinyin_ime::std::`。所以片段一律不写 include，依赖 `quick_input.h` 顶部的公共 include。

## 5. 验证（三条，都实跑过）

1. **预处理等价性（最强的一条）**：`git worktree add /tmp/oldwt HEAD` 取出拆分前的代码，新旧各跑一次
   `g++ -std=c++17 -E -P -I cpp cpp/quick_input_test.cpp`，去掉空行与行尾空白后逐行 `diff`：
   **两份都是 65561 行，差异 0 行**。token 流相同 ⇒ 对 CLI/addon 而言语义完全相同，不是"看起来像"。
2. **编译 + 单测**：`g++ -std=c++17 -O1 -I cpp cpp/quick_input_test.cpp` 编译通过；运行 **699 passed / 0 failed**。
3. **静态守卫**：`scripts/ci_static.sh` 全绿（43 项），其中新增 6 项拆分约束。

## 6. CI 新增的拆分守卫

写在 `scripts/ci_static.sh` 的 `=== quick_input.h 拆分 ===` 段：

- `quick_input.h` ≤ **400 行**（当前 104）——防止"拆完又塞回去"，这是本轮唯一能真正锁住成果的机制；
- 片段文件 ≥ 6 个；
- 片段内不得出现 `^namespace pinyin_ime` 声明（第 4 节的坑）；
- `quick_input.h` 必须包含每一个 `cpp/quick_input_*.h`（防孤儿片段：文件存在但没人 include，等于死代码）；
- `cpp/pinyin_ime_cli.cpp` 与 `fcitx5-addon/pinyinime.cpp` 不得直接 include 片段（只允许从 umbrella 进，否则顺序依赖会失控）。

## 7. 已知局限

- **addon 未编译验证**：本机无 fcitx5 5.1 头文件，addon 的编译只能留给用户沙箱或 CI。缓解手段是第 5 节的预处理等价性——token 流不变，addon 侧行为按定义不变。
- **片段不能单独编译**：它们依赖 umbrella 的 include 与 namespace。后续若要真正独立（可单独跑测试、可被其它 TU 复用），需要先解决跨片段依赖（`stats` → `CloudCandidate`、`boost` → 前 9 个片段的入口函数），那是一大步，不建议和这次混在一起。
- **没有解决重复实现**：本轮只做了"分家"，CLI 与 addon 里仍然各有一份英文判定/上屏逻辑。拆分让这些重复变得可见、可对比，但消除要靠下一轮抽 `core`。

## 8. 下一步建议

1. 消除 CLI/addon 重复实现（英文双写辅音判定 4 处 → 收进 `quick_input_core.h`），这需要 addon 能编译才能验证，因此优先解决"能编译 addon 的环境"。
2. 片段真正独立：先抽 `CloudCandidate` 到 `cpp/cloud_types.h`，解开 `stats` 对 `cloud` 的依赖，再让片段自带 namespace + include，CLI/addon 改为按需 include。
3. 真实引擎基线（`bench/baseline.json`）仍未产出，卡在"能编译 libime 1.1.x 的 Linux 机器"，与本轮无冲突但优先级更高——没有基线，后面所有功能改动都无法判断是变好还是变坏。
