# 模糊测试与两处性能/稳定性缺陷（v0.9.193）

> 2026-11-26 20:40 · 豆包 · 版本 0.9.192 → 0.9.193
>
> 方案：`docs/20261126-1920-测试开发升级方案-豆包.md`（P2 阶段）

## 1. 结论先行

新写的变异模糊测试**第一次跑就抓到崩溃**：`smart_segment` 递归回溯在 10 万字符输入下栈溢出（SIGSEGV）。同时测出「相邻字母交换纠错」是 O(n²)，10 万字符要 430ms。两处都已修掉：

| 输入 | 修复前 | 修复后 |
| --- | --- | --- |
| 100,000 个 `a`：`smart_segment` | **崩溃（栈溢出）** | 19ms，正常返回 10 万个音节 |
| 100,000 个 `a`：`quick_candidates_v5` | 464ms | 27ms |
| 100,000 个 `a`：`quick_candidates_v11` | 411ms | 24ms |
| 模糊测试 2000 次随机输入 | — | 无崩溃、无不变量破坏（ASan/UBSan 下 1000 次同样通过） |

## 2. 缺陷一：`smart_segment` 递归深度等于输入长度

原实现用 `std::function` 递归 `solve(pos)`，用「标记已计算」做记忆化。位置只增不减，看起来是 DAG 不会环，但**递归深度等于输入长度**：10 万个 `a`（每个都是合法音节）递归 10 万层，默认 8MB 栈直接爆。

改成从尾部向前的迭代 DP：`cnt[pos]`＝从 pos 到末尾最少音节数，`pick[pos]`＝选中的音节长度，最后正向重建结果。时间复杂度不变，栈深度恒定。

这类输入并非纯理论：按住一个键不放、或把长串误粘贴进预编辑，都能造出来。

## 3. 缺陷二：相邻字母交换纠错是 O(n²)

`typo_correction_lookup` 的「相邻交换」对每个位置都 `std::string swapped = input;` 拷贝整串再比较，长度 n 时是 O(n²) 且每步一次全量分配。真实预编辑不会超过几十字符，加长度上限 64（超出直接不做交换猜测），100k 输入从 430ms 降到 0。

## 4. 新增：`cpp/fuzz_segment_test.cpp` + `scripts/fuzz_test.sh`

不引入 libFuzzer（项目要求零额外依赖），用固定种子 xorshift 生成随机串 + 对抗性构造：

- 随机：大小写字母、空格、标点、中文词、**非法 UTF-8 续字节**、数字、`xi'an/xian` 混排，长度 0–200；
- 对抗：空串、单字符、10 万同字符、10 万空格、2 万次 `xi'an`、控制字符与 `\x80\xff`、`nihao+5000 个逗号`；
- 不变量：不抛异常；`disambiguate_pinyin` 输出不膨胀超过 2n+8；`pinyin_fully_segmentable` 同输入结果稳定；各版本候选条数 ≤64；超长输入耗时上限（普通 500ms / ASan 下 2000ms）。

`scripts/fuzz_test.sh` 自动选 ASan+UBSan（无 `/proc` 的 chroot 降级 UBSan），可用 `FUZZ_SEED` 复现。

## 5. 仓库卫生：71 个 `.gcov` 误入库

v0.9.192 调试覆盖率时在仓库根目录跑 `gcov`，生成的 71 个 `.gcov` 被 `git add -A` 一起提交了（patch 里 183 处 trailing whitespace 警告就是它们）。本轮 `git rm` 全部移除，并在 `.gitignore` 增加 `*.gcov` / `*.gcda` / `*.gcno`。
