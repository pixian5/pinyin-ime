# v0.9.210：软门限与 Top5 提升

## 问题

v0.9.209 的硬门限写成 `item.score -= 100.0f`：原 libime 分差超过 `kRerankBaseGate=1.0` 的候选几乎被直接踢出前排。Top1 从 30.17% 提到 30.92%，但 addon Top5 只有 45.17%，比不套门限的 4-gram 版本（45.92%）低 0.75pp。Top5 是长句输入的重要逃生口，不能为了 Top1 把它压没。

## 改动

1. `cpp/char_lm.h` 新增 `kRerankBasePenalty = 1.0f`。
2. addon / CLI 把低于门限的候选惩罚从 `-100` 改为 `-1`：仍然表达「原分差过大的候选降权」，但不再一票否决。
3. addon 的短候选条件从 `full[items[0].order].toString().size() >= 18` 改为 `items[0].text.size() >= 18`，与 CLI 一样按「过滤后的首个整句候选」判断；避免原始 `full[0]` 是短候选时误跳过门限。
4. `Item` 增加 `text` 字段，仅为上述判断服务。

## 结果

addon 1200 句真实上屏：

| 域 | Top1 | Top5 | Top10 | MRR | 字级 |
|---|---:|---:|---:|---:|---:|
| baike | 31.0% | 46.67% | 51.67% | 0.3818 | 89.17% |
| news | 40.33% | 54.33% | 58.33% | 0.4632 | 89.79% |
| recent | 33.33% | 50.0% | 52.67% | 0.4071 | 87.11% |
| wiki | 19.0% | 33.67% | 36.33% | 0.2534 | 79.71% |
| **合计** | **30.92%** | **46.17%** | **49.75%** | **0.3764** | **86.45%** |

对比 v0.9.209：Top1 30.92% 持平，Top5 45.17%→46.17%（+1.00pp），Top10 49.17%→49.75%（+0.58pp），MRR 0.3729→0.3764，字级 86.37%→86.45%。P50 490.3ms / P95 603.9ms / P99 696.3ms，与 v209 同量级。

CLI nbest=45 1200 句：Top1 **31.92%**（v209 31.67%，+0.25pp），Top5 **45.58%**（v209 45.17%，+0.42pp），域为 baike 32.0 / news 39.67 / recent 36.33 / wiki 19.67。

## 失败实验记录

- NBest=100：CLI 仅 +0.16pp，addon wiki 18.67% 低于 45 候选的 19.0%，P95 793ms；证伪。
- 局部同音词替换：`rewrite_dump` 能正确枚举词位同音词，但在 v209 重排 top1 上做替换，全量净收益 -2 句；阈值扫描最好也只 +1 句，证伪。
- 外部字符语料：把 LCCC base_valid 10k 句、人民网新增 649 句加入 clean 训练，Top1 分别 382/379，均未超过 380；词边界标记模型 354，更差。
- **假突破**：曾把 `bench/corpus` 原始 16k 句（含 eval-only 与 holdout 近似重复）直接训练，离线/CLI 得到 565/1200=47.08%。换成 `bench/clean_corpus.py` 的 12,130 句后回落到 372。该 47% 是训练集泄漏，不能作为模型收益；后续任何字符模型实验必须先走 clean split。

## 结论

软门限用很小的代价把 Top5 拉回并超过无门限版本，Top1 不降；这是 v0.9.210 的可交付点。Top1 继续停在 30.92% / CLI 31.92%，说明当前瓶颈不是门限强弱，而是候选池与重排模型本身。
