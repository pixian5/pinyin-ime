# 运行时冒烟、升级矩阵与 CI 真实构建（v0.9.195）

## 背景

v0.9.191–193 把静态检查、单测、覆盖率、sanitizer、fuzz、安装矩阵都脚本化了，但还有三块只靠「相信编译通过」：

1. **addon 从没在真实 fcitx5 进程里跑过**。编译链接成功、`--version` 正确，都不等于 fcitx5 会加载它，更不等于能打字上屏。
2. **升级/回滚没有验证**。v0.9.189 曾把 `libime-data` 的 `sc.dict` 当自己的旧数据删掉，这种问题只有装一遍旧版再升级才暴露。
3. **CI 没有真实编译 + 评测**。以前只有静态检查和不依赖 libime 的单测，编译失败、准确率退化都发现不了。

本轮三块全部补齐，并接入 `release_check.sh --full` 与 GitCode Actions。

> **后续更正（v0.9.196）**：GitCode 与 AtomGit 同平台但仓库 Actions 页不存在，本节所述 `.gitcode/workflows/ci.yml` 从未真正执行，已在 v0.9.196 移除；`scripts/ci_build.sh` 仅保留为本地门禁。详见 [20261126-2240-AtomGit-Action入口不存在与远端CI移除](20261126-2240-AtomGit-Action入口不存在与远端CI移除-豆包.md)。

## 一、fcitx5 运行时冒烟：`scripts/test_runtime_fcitx5.sh`

### 做法

没有桌面也能跑：私有 `Xvfb` 显示号（自动挑 90–110 里没被占用的）+ 私有 `HOME/.config/fcitx5/profile`（把 `DefaultIM` 设为 `pinyinime`）+ `dbus-run-session` 启动 `fcitx5 -D`。日志落到临时目录，按日志、D-Bus 和真实按键断言。

### 断言（6 项）

1. 日志出现 `Loaded addon pinyinime`
2. 日志出现 `pinyinime: loaded lm=... dict=...`（说明 LM/词典路径在真实安装布局下是对的）
3. 日志出现 `Found 1 input method(s) in addon pinyinime`（注册成功）
4. 没有 `Failed to create addon pinyinime` / `Could not load addon pinyinime`
5. 有 `python3-dbus` 时：`AvailableInputMethods` 里含 `pinyinime`，且 `SetInputMethodGroupInfo` + `SwitchInputMethodGroup` 成功
6. 有 `xdotool` + `python3-gi`/GTK3 时：开一个 GTK3 输入框，用 `xdotool` 真实敲 `nihao` + 空格，断言输入框内容为「你好」

没有 fcitx5 / Xvfb / `dbus-run-session` 时直接 SKIP 退出 0，不阻断开发机。

### 实测

在 chroot（Ubuntu 24.04 + fcitx5 5.1.7 + libime 1.1.5 + fcitx5-frontend-gtk3）里装 deb 后运行：

```
[info] addon: /usr/lib/x86_64-linux-gnu/fcitx5/libpinyinime.so
  [PASS] addon pinyinime 被 fcitx5 加载
  [PASS] addon 读取到语言模型/词典
  [PASS] pinyinime 注册为输入法
  [PASS] addon 加载无错误
  [PASS] OK: D-Bus 可见 pinyinime，输入法组切换成功
  [PASS] 真实按键上屏：nihao + 空格 → 你好（GTK3 + fcitx5 im module）

运行时冒烟：6 通过，0 失败，0 跳过
```

### 为什么用 GTK im module 而不是 XIM

先试的是 Xlib XIM 客户端（`XOpenIM` + `XCreateIC` + `XFilterEvent` + `Xutf8LookupString`）：

- XIM 能连上，客户端聚焦后 `CurrentInputMethod()` 返回 `pinyinime`；
- 但所有 KeyPress 都被 `XFilterEvent` 吞掉，之后收不到带 commit 文本的事件（只有 `MappingNotify`）；
- 在无窗口管理器的 Xvfb 下，焦点/IC 生命周期与真实桌面不同，判断是测试环境限制，不是 addon 问题。

改走 GTK3 + `GTK_IM_MODULE=fcitx`（fcitx5-frontend-gtk3）后一次成功：`xdotool type nihao`、`xdotool key space`，输入框 `get_text()` 返回「你好」。这是真正的「引擎 → 候选 → 上屏」端到端验证。

顺带确认的两件事：

- addon 的 `[Addon/Dependencies] core:5.1.7` 与 fcitx5 5.1.7 版本匹配，`loadAddon pinyinime checkDependencies() returns 0`。
- 组信息要通过 `org.fcitx.Fcitx.Controller1.SetInputMethodGroupInfo(group, layout, items)` 写入（接口名是 `org.fcitx.Fcitx.Controller1`，**没有数字 5**）。

## 二、升级矩阵：`scripts/test_upgrade_matrix.sh`

### 覆盖路径

deb 与 rpm 各跑一遍：

```
当前版安装（基线，记录 sc.dict + LM 的 md5）
  → 装旧版                （版本、解码、数据指纹不变）
  → 升级当前版            （版本、数据指纹不变、解码正常、addon 版本同步、.so 在位）
  → 降级回滚              （deb: --force-downgrade；rpm: -Uvh --oldpackage）
  → 再升级回当前版
  → 卸载                  （CLI/addon 移除，sc.dict 与 LM 仍在）
```

退出时 `trap` 无条件重装当前 deb，避免把测试机留在旧版。

## 四、顺带修出的真缺陷：runtime install.sh 在 headless 挂死

跑升级矩阵后的安装矩阵（`test_install.sh`）时，runtime 包的 `install.sh` 卡在 `fcitx5 -r`；修完后 `uninstall.sh` 又在同一步卡住（同一个毛病）：

- `fcitx5 -r` 在无 `DISPLAY` 的 chroot/容器里不会立刻失败，而是一直等 X 连接；
- 安装脚本是 `set -e` 且没有超时，整个安装流程就停在这里（实测卡了 10 分钟以上）。

修法（`scripts/build_packages.sh` 生成的 install.sh 与 uninstall.sh 都改了）：

```sh
if [ -n "${DISPLAY:-}" ] || [ -n "${WAYLAND_DISPLAY:-}" ]; then
    timeout 5 fcitx5 -r >/dev/null 2>&1 || true
fi
```

headless 环境直接跳过重载；有桌面时最多等 5 秒。`ci_static.sh` 加了守卫防回归。

## 五、接入门禁

- `release_check.sh --full` 新增两段：升级矩阵（阻断项）、运行时冒烟（失败阻断；SKIP 记为提醒）。
- `ci_static.sh` 新增守卫：两个脚本存在且可执行、运行时脚本保留 SKIP 分支与真实上屏断言、升级脚本有 deb/rpm 两段与数据指纹断言、`ci_build.sh` 与 workflow 存在且被引用。

## 踩过的环境坑（供复用）

- chroot 里 `/tmp/.X11-unix` 默认不存在，Xvfb 报 `Cannot establish any listening sockets`；先 `mkdir -p /tmp/.X11-unix && chmod 1777`。
- `pkill -f "fcitx5 -D"` 会匹配到包含这段文字的当前 shell，把自己杀掉（exit 137）；清理用 `pkill -x fcitx5`。
- 宿主机可能已有 `:99` 的 X socket（其他会话的 fcitx5），脚本因此从 90 起找空闲显示号，不写死 99。
- chroot 里 `pkill`/`ps` 依赖 `/proc`，无 `/proc` 时不可用；进程清理放在宿主执行。
- `ci_static.sh` 原来在 chroot（rsync 时排除了 `.git`）里跑 `git diff --check` 会直接 fatal；已改为「确实是 git 仓库才检查」，非仓库打印 SKIP。
- GTK 输入框在 Xvfb 下不需要窗口管理器，`xdotool search --name pinyin-ime-test windowfocus` 就能拿到焦点。

## 剩余缺口

- GitCode 的 `build-eval` job 用 `ubuntu-latest` 标签，远端 runner 是否提供该标签需首次推送后确认；若只有 `euleros-2.10.1`，需改自托管 runner 或加 Docker 镜像。
- XIM 前端在无窗口管理器的 Xvfb 下仍拿不到 commit 事件；真实桌面已由 GTK im module 路径覆盖。
