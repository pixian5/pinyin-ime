## 1. 结论先说

1. **"libime 1.1.x 编译不出来"是误判**：不是代码问题，是 Ubuntu 22.04 软件源只有 libime 1.0.11。换成 Ubuntu 24.04（libime **1.1.5**、fcitx5utils 5.1.7、Boost 1.83），`cmake -S cpp` 一次通过，`pinyin_ime_cli` 直接编出来。
2. **真实基线**（1200 句零泄漏 holdout，`--batch --top1`，system 词典 `sc.dict` + `zh_CN.lm`）：句级 **26.33%**、字级 **83.32%**。README 宣称的"字级 91% / 句级 68%"没有任何真实依据；旧的"77%→100%"、"189 条 100%"是语料与预设同改的自证（详见体检文档 P0-1）。
3. **修掉一个真缺陷**：合法拼音被判为英文、整句原样回显。修后同一语料字级 **84.26%**（+0.94pp）、句级 **26.67%**（+0.34pp）。

## 2. 构建链路（可复现）

```bash
# 1) 取 Ubuntu 24.04 base rootfs（29MB）
curl -LO https://cdimage.ubuntu.com/ubuntu-base/releases/24.04/release/ubuntu-base-24.04.3-base-amd64.tar.gz
mkdir noble24 && sudo tar -xzf ubuntu-base-24.04.3-base-amd64.tar.gz -C noble24
sudo cp /etc/resolv.conf noble24/etc/resolv.conf

# 2) 首次 apt 会因缺 gpgv 拒绝签名，先放行一次装 gnupg，再正常 update
sudo chroot noble24 bash -c '
  apt-get update -o Acquire::AllowInsecureRepositories=true
  apt-get install -y --allow-unauthenticated gnupg
  apt-get update'

# 3) 依赖（全部来自 noble 源）
sudo chroot noble24 bash -c '
  apt-get install -y build-essential cmake python3 libimepinyin-dev libimecore-dev \
                         libfcitx5utils-dev libboost-dev libcurl4-openssl-dev'
# libime 1.1.5-1 / fcitx5utils 5.1.7-1build3 / Boost 1.83

# 4) 编译（源码用 rsync 拷进 chroot；本容器不允许 bind mount）
sudo rsync -a --exclude .git . noble24/src/
sudo chroot noble24 bash -c 'cd /src && cmake -S cpp -B /tmp/build -DCMAKE_BUILD_TYPE=Release && make -C /tmp/build pinyin_ime_cli -j4'
```

运行时数据：LM `/usr/lib/x86_64-linux-gnu/libime/zh_CN.lm`（22MB），词典 `/usr/share/libime/sc.dict`（3.4MB），由 `libime-data` / `libime-data-language-model` 提供。

**addon 也能编了**（此前从未被编译验证过）：再装 `libfcitx5core-dev` + `extra-cmake-modules`，
`cmake -S fcitx5-addon -B /tmp/addonbuild && make` 一次通过，产出 `libpinyinime.so` 1.2MB。
顺带验证了 v0.9.178 的 `quick_input.h` 拆分：addon 侧编译无报错，与"预处理 token 流一致"的结论互相印证。

注意：chroot 里的二进制依赖 GLIBC 2.39，**只能在 chroot 内跑**，在 22.04 主机上会 `GLIBC not found`。

## 4. 修掉的缺陷：合法拼音被判英文

**现象**：1200 句里 13 句（1.1%）输出等于输入原文，即整行拼音被原样回显。

**定位**：

1. `boost_v11` 不是元凶——用 1200 句全量喂 `boost_v11`，命中率 **0.0%**，普通全拼根本不走增强入口。
2. 走到英文检测分支。旧 `is_valid_pinyin()` 是"最长音节贪心"：

```
guangxuershiwuniannianyinbingqushi
贪心：guang|xue|[r]|shi…      ← "xue" 抢走了 "xu"+"er" 的 "e"，剩孤立 'r'
结果：非法 → 判英文 → 原样回显
```

3. DP 兜底也没救回来：`dp_pinyin_segment()` 允许"单字符残段回退"，且以**音节数最少**为目标，`xue` 比 `xu|er` 少一段，于是照样产出残段 `r`，兜底判断仍旧失败。

**修复**：在 `cpp/quick_input_rank.h` 新增 `pinyin_fully_segmentable()`——只做**完整覆盖可达性**判断（每个位置都必须落在某个有效音节边界上，零残字），用同一份 410 条音节表。CLI 的 `is_valid_pinyin()` 改成薄封装，并删掉那份 412 条的静态音节表（重复数据源）。

同时加 8 条单测（`cpp/quick_input_test.cpp`）：长句覆盖、`nv`（ü 写法）、`hello`/`zzz` 反例、`banana`（ba|na|na 合法，说明英文误判只能靠"不可切分"这一条，不能靠"像不像拼音"）、以及与 `dp_pinyin_segment` 的分工声明（分词允许残段，不得用来判合法性）。

**效果**（同机器、同语料、同参数）：

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 句级 | 26.33% | **26.67%** | +0.34pp |
| 字级 | 83.32% | **84.26%** | +0.94pp |
| wiki 字级 | 74.4% | **76.38%** | +2.0pp |
| baike 字级 | 85.53% | 86.2% | +0.67pp |

## 6. 已知局限

1. 单机单环境：只有 `ubuntu-base-24.04` + `zh_CN.lm` 这一组数据，换 LM/词典数字会变，跨环境不可直接比。
2. holdout 的拼音由 pypinyin 生成，多音字按默认读音，个别句子本身存在"正确读音也解不出原字"的情况（例如人名、古文），这部分错误不该算到引擎头上，但当前没有剔除。
3. 逐句 52–82ms 是 `--batch` 冷启动逐行解码的耗时，不等于交互输入延迟（交互是逐键解码，另有开销）。
4. 13 句回显只修了"贪心误判"这一条路径；英文单词恰好在音节表内（如 `banana`）仍会被当拼音处理，这是启发式的固有限制，不是回归。
