# CLI 与纯库解码偏差归零（v0.9.182）

> 2026-11-26 17:40 · 豆包 · 版本 0.9.181 → 0.9.182

## 1. 问题

v0.9.180/0.9.181 的评测里一直有个说不清的口径差：

| 引擎 | 句级 | 字级 |
| --- | --- | --- |
| `libime_bench`（纯库，同 LM/词典，nbest=5） | 27.83% | 84.81% |
| `pinyin_ime_cli`（v0.9.179～181） | 26.67% | 84.26% |

差 1.16pp 句级 / 0.55pp 字级，但两边喂的是同一份输入、同一个引擎。此前排查过并**排除**的假设：

- `boost_v11` / `boost_abbreviation` 命中率：当时测出 0.0%（测法有误，见第 3 节）；
- `ctx.sentence()` 与 `candidatesToCursor()[0]` 不一致：1200 句 0 处不同；
- `nbest` 没生效：位置参数解析正常，10/20 也确实跑得更慢。

## 2. 定位过程

1. 用直连 libime 的探针（`/tmp/cmp.cpp`）在 1200 句上复算：**探针与 `libime_bench` 完全一致**，说明差在 CLI 自己的前后处理，不在解码库。
2. 逐行比对 CLI 与 bench 输出：初版 65/1200 行不同，且错得很怪——`xianzai` 的「现在」变成「西安」，`nianqing` 的「年轻」变成「尼庵」。
3. 顺着错字特征查调用链，定位到三处：
   - **`disambiguate_pinyin` 无条件对所有输入做音节拆分**：把连写全拼里的 `xian/nian/qian` 硬拆成 `xi'an/ni'an/qi'an`，于是「先/县」→「西安」、「年」→「尼庵」。这函数本来是为简拼/地名消歧写的。
   - **简拼启发式 boost 作用于纯全拼**：`suffix_boost` / `prefix_boost` / `vowel_tail_boost` 会把整句里已经正确的首选顶掉（「早期」→「早起」、「作用」→「预约」）。此前"命中率 0.0%"的测量只看了「boost 结果是否等于 gold」，把"boost 把对的顶成错的"漏掉了。
   - **v11 预解码捷径吞掉中文候选**：`--batch` 在解码前先跑 `boost_v11(line, {})`，非空就直接输出并 `continue`。于是输入 `xianzai`（现在）只会得到「2026年11月26日 17:34」，一条中文候选都没有；`boost_v11` 本身也是无条件把结果插到首位。

## 3. 修复（v0.9.182）

| 位置 | 改动 |
| --- | --- |
| `cpp/pinyin_ime_cli.cpp` | 新增 `disambiguate_if_needed()`：仅当输入**不是可完整切分的纯全拼**时才调 `disambiguate_pinyin`；批量与行模式两处调用点切换过去 |
| `cpp/abbr_presets.h` | 新增 `is_full_pinyin_input()`（纯字母 + `pinyin_fully_segmentable`）；`boost_abbreviation` 里三项启发式 boost 仅对简拼/混输生效，完整匹配预设与英文直通不受影响 |
| `cpp/quick_input_boost.h` | `boost_v11` 增加 `insert_v11()`：纯全拼输入时，时间/计算器/热词/快捷语/缩写结果**插到第一位候选之后**，不抢首位 |
| `cpp/pinyin_ime_cli.cpp` | 预解码捷径加 `v11_shortcut_allowed()`：`xianzai / shijian / riqi / xingqi` 这四个「本身是常用中文词」的触发词不再走捷径；`time / sj / date / xq` 等纯缩写仍可直接出时间 |

`--extra-dict`、模糊音、`nbest` 等既有行为不变。

- **准确率**（1200 句零泄漏 holdout，同机同 LM/词典，CLI `--batch --top1`）：

| 版本 | 句级 | 字级 |
| --- | --- | --- |
| v0.9.179（修英文误判） | 26.67% | 84.26% |
| v0.9.182（本轮） | **27.83%（+1.16pp）** | **84.81%（+0.55pp）** |
| 参考：纯库 `libime_bench` | 27.83% | 84.81% |

四域同步上涨：baike 25.0→26.0 / 86.25→86.80，news 34.0→35.0 / 87.73→88.11，recent 33.0→34.33 / 86.75→87.22，wiki 15.0→16.0 / 76.38→77.11。**CLI 与纯库逐句完全一致（1200/1200）**——代码侧不再有额外损失，剩下的差距只能靠换 LM/重排。

- **行为回归**：`bjdx→北京大学`、`nh→你好`、`wsm→为什么`、`zg→中国` 简拼 boost 正常；`xianzai→现在（首位）+ 日期时间（第二位）`；`time / sj` 仍直接出时间；`jintian→今天`。
- **单测**：716 passed / 0 failed（新增 9 条 v182 用例：全拼判定、启发式不劫持全拼、简拼仍生效、v11 让位、缩写仍置顶）。
- **构建**：chroot（Ubuntu 24.04 + libime 1.1.5）CLI 与 fcitx5 addon 均编译通过（`libpinyinime.so` 1,153,784 字节）。
- **CI**：`quick_input_test` 编译标准由 `-std=c++17` 对齐为 `-std=c++20`（与 `cpp/CMakeLists.txt`、`fcitx5-addon/CMakeLists.txt` 一致；`abbr_presets.h` 用了 `starts_with`，17 编译不过）。

## 5. 已知遗留

- addon 侧 `pinyinime.cpp` 仍有两处直接调 `disambiguate_pinyin`（第 793、1729 行），即 GUI 里打 `xianzai` 仍可能被拆成「西安在」。共享的 `boost_abbreviation` 守卫已随头文件生效，但 `disambiguate_pinyin` 的调用点需要单独验证（addon 只能编译、无法在本机跑 GUI）。
- `full_pinyin_preset_map` 里 `{"xian","西安"}`、`{"ji","鸡"}`、`{"yu","鱼"}` 这类单音节硬覆盖仍然存在，它们对整句评测无影响（整句不会精确等于单音节），但会让「打 xian 想选 先」时首位永远是西安。属产品取舍，未在本次改动。
- 91%/68% 目标仍不可达（recall@10 上限 46.08% 句级 / 90.21% 字级），下一步仍是重排与换 LM，而不是继续动解码壳。
