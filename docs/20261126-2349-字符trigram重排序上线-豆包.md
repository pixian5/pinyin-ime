# 字符 trigram 重排序上线（CLI + fcitx5 addon）

- 版本：v0.9.197
- 日期：2026-11-26
- 模型：豆包

> **重要更正（2026-11-27）**：本文的 42.67% / 88.88% 是训练集泄漏复现值，不能作为真实准确率。1200 句 holdout 原文全部来自训练用的 `bench/corpus`；去掉逐句原文重叠后重训，实测为 26.50% / 85.62%，不启用字符重排为 27.83% / 84.81%。评测修复方案见 [20261127-0111-项目整体分析与下一步开发建议](20261127-0111-项目整体分析与下一步开发建议-豆包.md)。

## 一、为什么要做

v0.9.180 测得纯库/CLI 基线为 **句级 27.83% / 字级 84.81%**，而 `nbest=10` 的 recall@1/@5/@10 为 27.83% / 41.42% / 46.08%，候选内字级上限 90.21%。这说明正解有相当一部分已经在候选里，只是被 libime 的原生打分排到了后面。v0.9.181 的词库扩充实验（5 万词全量导入）反而下降 0.46pp，因此本轮不再扩词典、不换 LM，改为用外部字符语言知识做重排序。

## 二、字符 trigram 模型

### 2.1 训练数据

- 训练语料：`bench/corpus/*.txt`，约 **324,490 字符**。
- 评测集：`bench/holdout` 1200 句；`python3 bench/check_leakage.py` 复核 **零泄漏**。
- 统计结果：词表 **4,212**（含 `<s>`/`</s>`/`<unk>`，实际汉字 4,209）；bigram **125,391** 条；trigram **245,842** 条；最大计数 16,178，全部可用 `uint16` 存储。

### 2.2 打分公式

整句字符 log 概率按 trigram / bigram / unigram 加权：

\[
\log P(s) = \sum_i \left(0.55 \cdot p_3(c_i \mid c_{i-2},c_{i-1}) + 0.30 \cdot p_2(c_i \mid c_{i-1}) + 0.15 \cdot p_1(c_i)\right)
\]

- unigram 使用 add-0.5 平滑；bigram / trigram 使用 add-0.1 平滑。
- 最终重排分数：`libime_score + alpha * logP(s)`，`alpha = 2.0`。
- 早期尝试只保留 `count >= 2` 的 n-gram，句级从 42.67% 掉到 32.58%，说明只出现一次的 trigram 仍然必要；最终保留全部条目。

### 2.3 二进制格式

`scripts/train_char_lm.py` 生成 `data/char_trigram.bin`，**3,502,768 字节**：

```
PICL + u16 version
词表（4,212 字）
unigram 计数
bigram 上下文 + 条目
trigram 上下文 + 条目
```

`cpp/char_lm.{h,cpp}` 用「排序数组 + `lower_bound`」加载到内存（约 3.4MB），启动读取一次。

### 2.4 C++ 与 Python 分数对齐时的坑

初版 C++ 在“上下文存在、目标字计数为 0”时直接回退 unigram，导致 `或者想象股市` 被高估（C++ -40.645 vs Python -41.622），整体增益只有 31.83%。修正为：上下文存在时即使目标字计数为 0，也按 `(0 + 0.1) / (contextTotal + 0.1 * V)` 做 add-0.1 平滑，**不能回退 unigram**。修正后 C++ 与 Python 逐字一致，重排结果恢复。

## 三、CLI 接入与结果

- `cpp/pinyin_ime_cli.cpp`：`collect_candidates()` 先取 `ctx.candidates()` 前 `max(nbest,10)` 个整句候选，按 `libime score + 2.0 * charLM.score(text)` 排序，再补 `candidatesToCursor()` 的词级候选。
- 新增全局 `g_charLM`、`--no-rerank` 开关；加载模型后 `ime.setNBest(max(nbest,10))`，保证 nbest=5 也能吃到前 10 候选。
- 模型查找顺序：`PINYINIME_CHAR_LM` → 当前目录 `data/char_trigram.bin` → `/usr/share/pinyin-ime/char_trigram.bin` → `/usr/local/share/...` → 可执行文件相对路径。

## 四、fcitx5 addon 接入

### 4.1 索引映射

addon 的 `refreshUI()` 用 `context_.candidatesToCursor()` 渲染，`selectCandidate(idx)` 直接把显示索引交给 `context_.selectCandidatesToCursor(idx)`。字符重排后必须新增「显示索引 → 原始候选索引」映射：

- `PinyinIMEState` 新增 `std::vector<size_t> displayToRaw_` 与 `bool rerankActive_`。
- `refreshUI()` 每次重建映射：
  1. 取 `context_.candidates()` 前 `max(10, nbest)` 个候选；
  2. 按 `score + 2.0 * charLM.score(text)` 稳定排序；
  3. 生成完整排列，未进入排序的词级候选按原序追加；
  4. 渲染循环用 `displayToRaw_[i]` 取文本；
  5. `selectCandidate()` 在云候选判断之后、libime 选中之前做一次反向映射。
- 简拼 boost 协调：若预设词已在候选内，把它在 `displayToRaw_` 中的显示位置挪到首位并清零 `boostSwap_`；若需要 `boostInsertWord_` 插入首位，则关闭本轮重排、退回原顺序，避免插入词造成索引错位。
- 云候选、翻页、`candFocus_` 仍按显示索引工作；映射只影响本地 libime 候选。

### 4.2 实测发现的真 bug：部分候选被排到首位

在真实 fcitx5 5.1.7 + GTK3 输入框里敲 `nihao` + 空格，首版重排后候选窗首选是 **「你」**，空格只选中第一个音节，`context_.selected()` 为 false，预编辑剩下 `你hao`，输入框最终为空。日志：

```
selectCandidate rawIdx=46 rawText=你 preedit=ni hao
selectCandidate selected=0 sentence=你好 preeditAfter=你hao
```

原因：`context_.candidates()` 不只包含覆盖整段拼音的整句候选，还混有只覆盖首音节的候选（`你`、`年` 等）。这些短候选的 libime 分数高，字符分也不低，重排后自然排到首位；选中它当然只吃掉第一个音节。

修复：重排前用 `context_.candidateFullPinyin(full[i])` 取出候选的完整拼音，与当前 `context_.preedit()` 的紧凑拼音长度比较，**只保留长度相等的整句候选**；该过滤只对全拼输入启用，简拼/混输不参与。

长度比较还要处理 `ü`：输入通常写 `lv`，而 `candidateFullPinyin` 可能返回 `lü`（UTF-8 两字节）。如果直接按 ASCII 字母过滤，`ü` 会被丢掉，导致合法整句候选被误杀——CLI 实测会从 42.67% 掉到 41.75%。为此新增 `pinyin_ime::compactPinyin()`，把 `ü/Ü` 归一成 `v` 后再比较；恢复后 CLI 仍是 42.67% / 88.88%。修复后 `nihao` + 空格在真实 fcitx5 里稳定上屏「你好」，运行时冒烟 **6/6**。

### 4.3 重排池大小

addon 实测 `context_.candidates()` 有 780 条（包含大量短候选），不能全部打分。重排池改为 `max(10, config().nbest)`（默认 45），只对前 45 条做字符打分；这既覆盖 nbest 候选，又避免每个按键对 780 条文本做二分查找。

### 4.4 打包时暴露的 runtime 卸载 bug

为了让 addon 在安装后也能找到模型，`build_packages.sh` 把 `data/char_trigram.bin` 装到 `/usr/share/pinyin-ime/`。新增「runtime 卸载后模型已移除」断言后，安装矩阵第一次跑就失败：模型文件残留。

根因不在卸载逻辑本身，而在 `install.sh` 生成清单时用了：

```sh
find usr -type f | sed 's#^usr/#/#'
```

`usr/share/...` 被改写成 `/share/...`，少了 `usr`。CLI（`/usr/bin`）和 addon（`/usr/lib`）恰好能通过 `/bin`、`/lib` 这两个符号链接命中，所以此前的「卸载干净」断言一直没暴露；模型放在 `/usr/share`，没有对应符号链接，才把问题显出来。

修复为：

```sh
find usr -type f | sed 's#^#/#'
```

第二次跑又暴露第二个问题：修正清单后，`uninstall.sh` 把 runtime 自带的 `/usr/share/libime/sc.dict` 删了。原逻辑靠 `dpkg -S` / `rpm -qf` 判断文件是否属于系统包，但 chroot / 手工部署环境里这两个命令可能都不认领。修复策略是：**`/usr/share/libime/` 下的 LM/词典一律视为共享数据，runtime 卸载永远保留**。最终安装矩阵 **30/30 通过**。

## 六、已知限制

- 字符模型只利用字符 trigram，不理解词边界；wiki 域仍只有 82.55% 字级，说明域外知识不足。
- 重排池受 nbest 限制，nbest=5 的用户只能吃到前 10 个整句候选；再往上提升需要换 LM 或扩大候选池。
- 模型 3.4MB 已入仓；若后续仓库体积敏感，可改为构建时生成，但当前发布包依赖它，必须保证安装路径。
- addon 只在 fcitx5 5.1.7 + GTK3 下做了真实按键验证；其他前端（Qt、Wayland、XIM）尚未逐一回归。
- 字符分 alpha=2.0 是在当前 holdout 上调出的，换语料/换 LM 后需要重新网格搜索。
