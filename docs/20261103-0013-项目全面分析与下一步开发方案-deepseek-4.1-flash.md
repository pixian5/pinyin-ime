## 0. 结论摘要

**项目已经"能跑、能装、功能多"，但"测得准"和"改得对"这两个环节断了。**

三条核心判断：

1. **评测口径与真实产品脱节**。当前唯一的准确率基线 `scripts/eval_baseline.json`（v0.9.67）来自
   `pinyin_ime_smart.py`（Python 包装：CLI + 长句切分 + 频率 boost + 后纠错），
   而用户实际使用的 CLI 交互模式与 fcitx5 addon **都没有**这三层后处理。
   也就是说：**发布的数字不是用户体感**。
2. **从 v0.9.68 到 v0.9.163，近 100 个版本没有一次可信的准确率回归**。
   主线转向"搜狗式功能 + 打包 + 部署"，新增皮肤、云拼音、剪贴板、输入统计、DP 分词等大量功能，
   但没有一次用统一口径验证"是否拉低整句准确率"。
3. **双前端已事实分叉，且新功能几乎全部堆在 CLI 侧**。本轮 37 个提交中，
   i 模式、u 模式、Tab 补全、云拼音、剪贴板、输入统计都只在 CLI；
   fcitx5 addon 只补了皮肤和表情面板。CLI 3239 行、addon 1624 行、`quick_input.h` 5267 行。

**建议主线**：先"可信化"（统一评测 + 版本单一来源 + 清理仓库回归），
再"统一架构"（拆掉万能头文件、抽公共核心库），最后才是"准确率冲刺"（LM 交付 + 纠错升级）。
**顺序不能颠倒**——否则准确率改动无法判断好坏，功能改动要写两遍。

## 2. 体检发现（按严重度）

### P0-1 评测口径与产品脱节（最高优先级）

**证据**

- `scripts/eval_baseline.json` 的 `description` 明确写着 `"CLI + post-correction (smart.py)"`。
- 全仓库检索：`cpp/pinyin_ime_cli.cpp` 与 `fcitx5-addon/pinyinime.cpp` 中**没有任何**
  `post_corrector` / 长句切分调用；`post_corrector.py` 只被 `pinyin_ime_smart.py`、`web_demo_v2.py`、
  `pinyin_ime_corrected.py` 使用。
- 本轮 37 个提交中，`git log --grep "准确率|评测|bench"` **没有任何评测提交**。

**影响**

- 无法判断新增的皮肤、云拼音、DP 分词、纠错增强是提升还是回退。
- 对外文档（README、PROJECT_STATUS、docs/EVALUATION.md）中的准确率数字互不可比。

### P0-2 版本号多处漂移，且 README 自身有 5 个"当前版本"

| 位置 | 值 |
|---|---|
| `VERSION` | **0.9.163** |
| `cpp/pinyin_ime_cli.cpp` `--version`（[L912](../cpp/pinyin_ime_cli.cpp)） | **0.9.86**（硬编码） |
| `README.md` 顶部（本次补充的进度块） | 0.9.126（已过期） |
| `README.md` 正文 | 同时存在 v0.9.129 / v0.9.128 / v0.9.127 / v0.9.125 / v0.9.121 五个"当前版本"标题 |
| `CHANGELOG.md` 最新条目 | v0.9.121 |
| `PROJECT_STATUS.md` 头部 | v0.9.121 |
| `PROJECT_RULES.md` "当前版本" | 0.9.50 |

**根因**

- 版本号只在 addon 的 CMake 里读取了 `VERSION`，但紧接着
  `set(PINYINIME_VERSION ${PROJECT_VERSION})`（[CMakeLists.txt L29](../fcitx5-addon/CMakeLists.txt)）
  又把唯一来源覆盖回 `project(... VERSION ...)`。
- CLI 完全没有版本生成机制，只能手写，于是从 0.9.86 之后再未同步。

### P0-3 "模糊音禁令"与代码正面冲突（比初版更严重）

- `README.md` 顶部仍声明：模糊音是**硬性禁令**，`common_fuzzy_flags()` 返回空集、`setFuzzyFlags()` 永不被调用。
- 但本轮新增的 `v0.9.135: 模糊音（Fuzzy Pinyin）— z/zh c/ch s/sh n/l an/ang 等` 明确实现了模糊音；
  代码中：
  - CLI [L220](../cpp/pinyin_ime_cli.cpp) `common_fuzzy_flags()` 返回全套 flag，
    [L1597](../cpp/pinyin_ime_cli.cpp) 调用 `setFuzzyFlags`。
  - addon [L747](../fcitx5-addon/pinyinime.cpp)、[L802](../fcitx5-addon/pinyinime.cpp) 按配置调用。
- README 另一处（约 L8070）还写着"设计禁令保持：模糊音仍然硬性禁止"。

**结论**：这不是"文档过时"，而是**两个相互否定的决策同时存在**。
必须由你明确拍板，否则后续任何评测结论都不可靠。

### P1-8 双前端逻辑重复且分叉

- CLI 3239 行 / addon 1624 行，重复实现：音节合法性判断、英文混输判定、标点转换、撤回、boost、
  表情、v 模式、日期/计算器/货币/单位。
- 英文判定仍是"24 个双写字母逐个 `find`"，CLI 与 addon 各一份。
- 分叉结果：桌面用户拿不到 i 模式、联想词、u 模式、Tab 补全、云拼音、剪贴板、输入统计。

### P1-9 长句准确率与 LM 体积的矛盾未解决

- `RESULTS.md` 已证明：现代 LM（5.59 亿词，765MB）在 4 个干净域句级平均 **+5.62pp**，
  剪到 p1（374MB）几乎无损（-0.05pp），p2 为 299MB（-0.60pp）。
- 但**没有交付**：安装包仍只带官方 34.7MB `zh_CN.lm`；增强模型没有下载通道、没有配置项、没有评测门禁。
- 延迟瓶颈在未剪的 bigram（5490 万），而不是 trigram——"压体积"和"压延迟"是两条不同的路。

### P1-10 纠错模块能力偏弱，且位置不对

- `PROJECT_STATUS.md` 记录：delete top1 **12.14%**、substitute **27.62%**。
- 纠错作用于"整串拼音 → 改写后再解码"，而不是在解码栅格内扩展候选；
  对"合法但选错"的同音歧义无能为力。
- 1.9MB 数据被编译进二进制，任何数据更新都要重编译。

### P2-11 工程卫生问题

- 内置简拼预设约 350 条，纯手工维护、无评测审计，存在过拟合风险。
- `u` 模式只有 48 条笔画表（`stroke_table()`），不是真正的笔画输入，却已按"功能"宣传。
- `scripts/` 大量硬编码 `/root/workspace/...`，脱离原沙箱即不可用。
- README 新段落标题写"2025-01"（应为 2026-10/11），时间线错误。

## 4. 详细设计方案

### D1 统一评测与回归门禁

#### 目标

一条命令，对**真实交付物**产出可比较的准确率/延迟报告，并在回退时自动失败。

#### 现状问题

`bench/run_bench.py` 调的是 `cpp/libime_bench`（一次性整句、无 boost/切分/纠错）；
`eval_baseline.json` 调的是 Python 包装；两者都不是产品。

#### 设计

新增唯一入口 `bench/eval.py`，适配器模式：

```
bench/
├── eval.py                 # 唯一入口：选引擎、跑语料、出报告、比对基线
├── adapters/
│   ├── cli_batch.py        # 调 pinyin_ime_cli --batch --top1（真实 CLI 管线）
│   ├── addon_e2e.py        # 调 testfrontend/XIM，抽样 100 句（真实桌面管线）
│   └── python_smart.py     # 旧口径，仅作历史对照，不再作为基线
├── configs/
│   ├── corpora.yaml        # 域 → 语料路径 / 是否 holdout
│   └── baseline.json       # 冻结基线：版本 + commit + 指标
└── results/<version>/      # summary.json + report.md + 错例明细
```

指标 JSON（稳定 schema，供门禁读取）：

```json
{
  "version": "0.9.164",
  "commit": "71b03bc",
  "engine": "cli-batch",
  "pipeline": ["boost", "split", "correct"],
  "domains": {
    "news": {"sentences": 200, "sent_acc": 40.5, "char_acc": 88.4,
             "first_word_top1": 0.0, "p50_ms": 0.0, "p99_ms": 0.0}
  },
  "overall": {"sent_acc": 0.0, "char_acc": 0.0}
}
```

门禁规则（`--compare baseline.json`）：

- 句级准确率下降 > **1.0pp** → 失败
- 字级准确率下降 > **0.5pp** → 失败
- P99 延迟上升 > **20%** → 失败
- 新增功能若只影响特定域，允许在配置里声明"豁免域"，但必须在 commit 说明理由

#### 实施步骤

1. **冻结现状**：先用 `pinyin_ime_cli --batch --top1` 跑 6 个域，生成 `baseline.json`。
   这是"改前"数字，之后所有改动都必须对它负责。
2. 把语料一次性转成拼音输入文件并缓存（`pinyin + hash → 文件`），避免每次重新 `pypinyin`。
3. CLI 增加 `--bench-json`（稳定 schema，不与人读的 `--json` 混用）。
4. addon 抽样集：用现有 `testfrontend` 驱动 100 句日常 + 50 句新闻，只用于验证"桌面管线与 CLI 一致"，
   不承担全量评测（太慢）。
5. `scripts/ci_eval.sh`：CI 里跑 daily（49 句）+ news（200 句），失败即阻断合并。

#### 验收

- `python3 bench/eval.py --engine cli --all --out bench/results/0.9.164` 在本机 Docker（linux/arm64）与 openEuler 均可跑通。
- 报告包含：版本、commit、每域指标、Top-20 错例（拼音 → 期望 → 实际）。
- 故意回退一处（例如关掉 boost），门禁能报红。

### D2 拆解万能头 + 抽取公共核心库（最关键的结构性改造）

#### 目标

CLI 与 fcitx5 addon 共用同一套候选生成管线；前端只负责"按键 → 核心 → 渲染/上屏"。
同时把 5267 行的 `quick_input.h` 按职责拆开。

#### 目标结构

```
cpp/
├── core/
│   ├── engine.h/.cpp        # libime 封装：加载 LM/dict、上下文、学习、落盘
│   ├── pipeline.h/.cpp      # 候选管线：boost → 分词/断句 → 纠错 → 频率 → 排序
│   ├── segmenter.h/.cpp     # 音节 DP 切分 / 长句断点
│   ├── presets.h/.cpp       # 简拼预设 + 热词（改为运行期加载数据文件）
│   ├── punctuation.h/.cpp
│   ├── text_utils.h/.cpp    # UTF-8、全半角、繁简
│   └── version.h.in         # configure_file 生成，唯一版本来源
├── input/
│   ├── quick_input.h/.cpp   # v/i/u/日期/货币/单位/计算
│   ├── skin.h/.cpp          # 皮肤/主题（仅渲染层使用）
│   ├── emoji.h/.cpp         # 表情分类/搜索
│   └── clipboard.h/.cpp     # 剪贴板历史
├── cloud/
│   └── cloud_pinyin.h/.cpp  # 云端候选（可禁用、带缓存与降级）
├── cli/main.cpp             # 参数解析 + 键循环 + 终端渲染（目标 < 800 行）
└── correction/              # 纠错算法（被 core 调用）
```

核心接口（示意）：

```cpp
struct InputOptions {
    bool boost_presets = true;
    bool split_long_sentence = true;
    bool correct = true;
    bool quick_input = true;
    int nbest = 45;
};

struct Candidate {
    std::string text;
    double score = 0.0;
    enum Source { LM, BOOST, QUICK, PREDICT, CLOUD } source = LM;
};

struct Result {
    std::string preedit;                // 音节分隔后的预编辑
    std::vector<Candidate> candidates;  // 已按统一顺序排好
};

class PinyinCore {
public:
    bool load(const CoreConfig &cfg);
    Result update(const std::string &raw_input, const InputOptions &opt);
    std::string commit(size_t index, bool learn = true);
    void backspace();
    void reset();
    void save();
};
```

关键约束：

- **管线顺序固定且可开关**，CLI 与 addon 传入同一个 `InputOptions`；
  评测时打印实际生效的管线，避免再次出现"评测跑的是一套、用户用的是另一套"。
- 前端**不允许**再做候选排序后处理；所有 boost/纠错/切分只在 core 内发生一次。
- 渲染（候选窗 vs 终端）留在前端；皮肤/表情面板属于渲染层，不进入 core。
- 云拼音必须默认关闭，且离线时静默降级（现在 README 已记录有 5 个云缓存测试长期失败）。

#### 迁移步骤（每步都可独立提交、独立验证）

1. 先按职责拆分 `quick_input.h`：`quick_input` / `skin` / `emoji` / `clipboard` / `cloud`，
   只移动代码、不改行为，跑现有 553 条测试确认。
2. 抽纯函数与 `segmenter`（无 libime 依赖，风险最低）。
3. 抽 `engine`：把 CLI 里的 `PinyinIME` 构造、数据路径探测、用户学习落盘搬进 core。
4. 让 CLI 接 core，跑 D1 门禁，确认指标不变（应完全一致）。
5. 让 addon 接 core，跑现有 E2E（XIM/GTK/Qt），确认行数下降且行为一致。
6. 删除重复实现与死代码（含未被引用的 `wayland_integration.h`）。

#### 验收

- `cpp/pinyin_ime_cli.cpp` < 800 行；`fcitx5-addon/pinyinime.cpp` < 900 行；`quick_input.h` 拆分后单文件 < 800 行。
- 两个前端链接同一个 `pinyin_core` 静态库。
- D1 基线在迁移前后**逐域一致**（允许 ±0.1pp 浮点噪声）。
- `git grep "double letter"` 只剩一份实现。

### D3 增强语言模型交付

#### 目标

把已验证的 +3～8pp 准确率增益真正交到用户手里，且体积/延迟可接受。

#### 设计

**双档模型（profile）**

| profile | 内容 | 体积目标 | 默认 |
|---|---|---|---|
| `standard` | 官方 `zh_CN.lm` 34.7MB | — | ✅ |
| `enhanced` | 现代语料 LM，剪枝 + 量化 | ≤ 300MB | 可选下载 |
| `experimental` | 4-gram / 新配比 | 不承诺 | 仅评测 |

**压缩路线（按收益/风险排序）**

1. 已完成的 trigram 剪枝：p1（374MB，-0.05pp）、p2（299MB，-0.60pp）。
2. 继续剪 bigram（`--prune 0 1 1`）——这是延迟瓶颈所在，需单独评测精度代价。
3. 量化位宽：现有 `-q 4`，试 `-q 3 / -q 2`，测体积、精度、延迟三维。
4. 4-gram：仅在 1–3 都到瓶颈后再上，且必须有 D1 门禁证明收益。

**交付方式**

- `scripts/fetch_lm.sh --profile enhanced` 从 S3 下载 + SHA256 校验 + 安装到用户数据目录。
- addon 配置新增 `LMProfile`（`standard` / `enhanced`），启动时按可用性回退。
- 安装包**不内置**大模型，避免 RPM/DEB 体积爆炸。

**验收**

- enhanced ≤ 300MB，在 news/recent/baike/wiki 四域句级平均 ≥ +3pp；
- 逐键 P99 不超过 standard 的 1.2 倍；
- 安装/切换/回退有脚本与文档，断网时自动回退 standard。

### D4 纠错升级（从"事后改写"到"解码期扩展"）

#### 现状

- M3 纠错是"整串拼音改写 → 再解码"，只对"拼错"有效，对"拼对但选错"无效。
- 指标：delete top1 12.14%、substitute 27.62%，明显低于 insert 78.10%。

#### 设计

**阶段 A：音节级混淆扩展（先做，风险低）**

1. 对输入做音节 DP 切分（403 个合法音节）。
2. 每个音节生成混淆集合：
   - 平翘舌：`zh↔z`、`ch↔c`、`sh↔s`
   - 前后鼻音：`an↔ang`、`en↔eng`、`in↔ing`、`ian↔iang`、`uan↔uang`
   - `n↔l`、`f↔h`、`v↔u`
3. 在音节级做 beam search，编辑距离 ≤ 2；代价 = 键盘物理距离 + 混淆先验。
4. 每个变体走 libime 解码，取 top-N，合并后按
   `score = LM_score + λ·log P(变体|原串)` 重排。
5. **门控**（防误伤）：
   - 原串是合法音节序列且 top1 存在 → 默认不纠错；
   - 仅当原串无法完整切分，或 top1 置信度低于阈值时启用；
   - 英文输入（不含任何合法音节前缀）直接透传。

**阶段 B：数据驱动先验（后续）**

- 用撤回记录（Ctrl-Z / 误上屏）与合成错拼语料，统计真实变换概率，替换手工先验。
- 可选：小型 seq2seq（ONNX）只在"整串重排"时调用，不进入逐键热路径。

**工程改造**

- 删除 `cpp/correction_data.h`（188,950 行），改为 `data/correction/*.bin`，运行期 mmap。
- 纠错只在**上屏/空格**时触发，不进逐键路径，延迟预算 50ms。

**验收**

- `correction/metric.py`：delete top1 ≥ 35%、substitute top1 ≥ 45%；
- 2000 句合法全拼语料上**零误纠**（top1 与原管线一致）；
- 新增 200 条错拼用例进单测。

## 6. 风险与回滚

| 风险 | 触发信号 | 回滚方式 |
|---|---|---|
| 评测框架改动导致数字不可比 | 同版本两次跑分差异 >0.2pp | 保留 `python_smart` 适配器作对照；基线 JSON 入库 |
| 核心库迁移引入行为差异 | D1 某域下降 >1pp | 按提交粒度迁移，每步可 revert；保留旧二进制产物 |
| 大 LM 下载失败/占满磁盘 | 安装后体积 >300MB 或下载中断 | profile 回退 `standard`；安装脚本做空间预检 |
| 纠错误伤合法输入 | 新闻语料 top1 变化率 >0.5% | 门控阈值可配置；默认只对非法切分启用 |
| 模糊音禁令影响现有用户 | 用户反馈无法输入 | 保留一个版本的兼容开关，随后删除（项目为开发测试版，可接受） |
| 删除预置/皮肤等"功能"导致回归 | 用户实际使用报告 | 功能级开关 + 单测保留，先下线数据而不是删代码 |
