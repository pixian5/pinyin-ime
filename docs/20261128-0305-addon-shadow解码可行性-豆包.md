# addon shadow 解码可行性实验

## 目标

在不破坏 addon 主 `PinyinContext` 的前提下，用独立上下文对整串拼音做一次批量解码，验证能否把 CLI 的长句重排收益搬进真实上屏。

## 实验 1：空格时临时 shadow，只提交 shadow 首选

在空格分支里新建 `PinyinContext shadow(ime_)`，整串重放并重排，然后直接提交首选。这样不影响组合过程中的显示，只测 shadow 的选句质量。

400 句（每域 100）：

| 配置 | Top1 | 说明 |
|---|---:|---|
| v0.9.212 基线 | 30.75% | baike 30、news 46、recent 31、wiki 16 |
| shadow NBest60 + β0.4 | 30.75% | baike 29、news 46、recent 32、wiki 16 |
| shadow NBest45 + β0.4 | 31.0% | baike 29、news 48、recent 31、wiki 16 |
| shadow NBest45，覆盖所有长度 | 31.25% | baike 30、news 48、recent 34、wiki 19 |

长句单独取 320 句（每域 80，拼音 ≥54）：基线 25.94%，shadow NBest60 为 27.19%，净增 1.25pp，但 baike 从 25.0 掉到 22.5。

结论：shadow 在“只提交首选”模式下有 0～0.5pp 的整体收益，长句子集约 1.25pp，但收益不稳定且 wiki 仍低。

## 实验 2：shadow 首选接入显示（两种实现都失败）

实现 A：在 `updateUI` 里用共享 `ime_` 建 shadow，把首选塞进 `boostInsertWord_` 显示。400 句 Top1 直接掉到 0%～2%，字级 2.5%～0.1%。原因是共享 `PinyinIME` 的 `PinyinContext` 会动到主上下文状态。

实现 B：引擎启动时再建一个独立 `PinyinIME`（重新加载 `zh_CN.lm` 与 `sc.dict`），shadow 用它解码，主上下文不动。400 句仍然 0%～2%，字级 0.1%～2.7%，且部分句子把上一句上屏文本带了进来。

结论：即使解码器独立，`updateUI` 内同步构造 shadow 并插入 `boostInsertWord_` 也会破坏候选映射/提交时序；当前架构下不能把 shadow 候选混进主候选列表。

## 边界

- 只提交 shadow 首选的模式没有 UI 一致性：显示的首选还是主 context 的，用户按空格却得到另一个词，不能上线。
- 接入显示需要把“显示候选、分页、数字键、鼠标点击、焦点、撤销”全部改到一个独立候选空间，不能复用 `boostInsertWord_` 这种单点插入。
- 独立 `PinyinIME` 会再加载一份 LM，内存和启动成本翻倍；本轮未做长期内存测试。
- 生产 v0.9.212 已恢复，8 句真实上屏 8/8 通过。

## 后续建议

shadow 若继续做，必须是“独立候选空间”而不是“插入一个候选”：`shadowActive_` 时 `updateUI`、`selectCandidate`、翻页、数字键、点击、撤销都走 shadow 列表，主 `PinyinContext` 只负责预编辑。这个改造量大于参数调整，收益上限约 1～2pp，需单独排期。
