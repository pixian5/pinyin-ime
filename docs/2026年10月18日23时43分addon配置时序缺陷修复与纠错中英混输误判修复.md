## 一、缺陷 1：conf 里的 DataDir/UserDataDir 不生效（配置时序）

### 现象
`~/.config/fcitx5/conf/pinyinime.conf` 里设置：

```ini
DataDir=/workspace/native-build/opt/libime/lib
UserDataDir=/tmp/ud-test
EnableCorrect=True
```

实际运行时（fcitx5 XIM/X11 模式 + DBus 模式）日志显示：

```
pinyinime: loaded lm=/root/.local/pinyin-ime/share/libime/libime/zh_CN.lm   ← 编译默认值，不是配置值
```

而 `EnableCorrect`（bool）却生效——「纠错生效但路径不生效」是典型线索：
**bool 配置在引擎创建后被 `reloadConfig()` 热更新；路径配置只在 `ensureDataLoaded()`（引擎创建）时读取一次，此时配置尚未加载。**

### 根因
`PinyinIMEEngine` 构造函数原顺序：

```cpp
PinyinIMEEngine::PinyinIMEEngine(Instance *instance) : instance_(instance) {
    instance_->inputContextManager().registerProperty("pinyinimeState", &factory_);  // ①
    reloadConfig();                                                                   // ②
}
```

fcitx5 的 `InputContextManager::registerProperty()` 在注册时会**立即为已存在的
InputContext 调用 factory**。XIM server / DBus 先建 IC、addon 后加载，构造 addon
时 IC 已存在 → ① 触发 factory → `ensureDataLoaded()` → 此时 `config_` 还是
**编译默认值**（`/root/.local/pinyin-ime/share/libime`），引擎被用错误路径创建。
② 才读取 `conf/pinyinime.conf`，但 `ime_` 已建，路径不再重读（设计如此，避免热更新中途换词典）。

DEBUG 日志的时序证据（修复前）：

```
DEBUG ensureDataLoaded: dataDir=[/root/.local/pinyin-ime/share/libime]   ← 默认值（先）
pinyinime: loaded lm=/root/.local/...
DEBUG reload: DataDir=[/workspace/native-build/opt/libime/lib] ...       ← 配置值（后）
```

### 修复（pinyinime.cpp）
先读配置，再注册 property：

```cpp
reloadConfig();                                        // ① 先读 conf
instance_->inputContextManager().registerProperty(..., &factory_);  // ② 再注册（触发加载时配置已就绪）
```

### 验证（DISPLAY=:88，全新 Xvfb + fcitx5）
```ini
DataDir=/workspace/native-build/opt/libime/lib
UserDataDir=/tmp/ud-fix88
EnableCorrect=True
EnableFuzzy=True
FuzzyC_CH=True
```

- 日志：`loaded lm=/workspace/native-build/opt/libime/lib/libime/zh_CN.lm`（配置值，✅）
- `/tmp/ud-fix88/` 新生成 `user.dict` / `user.history`（UserDataDir 生效，✅）
- 旧默认目录 `~/.local/share/pinyin-ime` 无新写入（mtime 未变，✅）
- `senme→什么`（M3 纠错）、`cifan→吃饭`（c→ch 模糊音）均 ✅

### 影响面
- 修复前「主链路能跑通」纯靠 `/root/.local` → `/workspace/.local` 符号链接把默认
  路径兜住；真实机器上用户配置 DataDir/UserDataDir 会**静默失效**。
- 此缺陷自 addon 初版起就存在，与 v0.9.100/101 的行为无关；重构「注册/加载」顺序
  的意识来自本机重编 addon 后可调试才暴露。

## 二、缺陷 2：`zhing` 纠错成功后仍被当英文原样上屏（中英混输误判）

### 现象
XIM 用例 `zhing→中`（M3 纠错边界，历史对拍含 `zhing→zhong`）失败：

```
FAIL  纠错边界 zhing→中  -> COMMIT:zhing
```

同组 `zhng→中`、`senme→什么`、`zongguo→中国` 均通过。

### 根因
空格上屏处理顺序：

1. 纠错（EnableCorrect）：`zhing` → `correct_to_string` → `zhong`，
   `ctx` 被改写为 zhong；
2. 中英自动混输（v0.9.100 引入）随后判断：

```cpp
if (!rawInput_.empty() && !is_valid_pinyin(rawInput_)
    && (ctx.candidates().empty() || rawInput_.size() > 4)) {
    commitText(rawInput_);   // 直接上屏「英文」
}
```

`rawInput_` 是**纠错前的原始串** `zhing`：`is_valid_pinyin("zhing")` = false
（zhi+ng、zhin+g 均非法），且长度 5 > 4 → 条件成立 → **原样上屏 `zhing`**。

`zhng`（4 字符）则因 `rawInput_.size() > 4` 不成立、且纠错后 `ctx.candidates()`
非空而躲过此误判。

### 修复（pinyinime.cpp）
纠错成功（`fixed != cont`）改写 `ctx` 时，同步 `rawInput_` 为纠正后的紧凑串
（去 `'` 与空格）：

```cpp
state->rawInput_.clear();
for (char c : fixed)
    if (c != '\'' && c != ' ') state->rawInput_.push_back(c);
```

此后 `is_valid_pinyin("zhong")` = true → 不进入英文分支 → 正常走候选上屏「中」。

### 验证
- 同一 DISPLAY（:90）完整重跑 21 项：**21/21 全过**（含 `zhing→中`）。
- hello 英文用例不受影响（`should_correct("hello")` 不成立，rawInput_ 不变）。

## 四、防回归要点

1. **addon 构造函数永远「先 reloadConfig，后 registerProperty」**：registerProperty
   会同步触发已存在 IC 的 property 工厂，任何工厂内读取配置的路径都依赖此顺序。
2. **纠错改写解码串时，必须同步 rawInput_**：中英混输判断读的是 rawInput_，
   两者语义一旦脱节就会出现「纠错成功但被当英文」这类隐蔽误判。
3. 测试脚本已支持 DISPLAY 参数化（`DISPLAY=:88 bash scripts/xvfb_ime_test.sh`），
   本机因 PID namespace 隔离无法跨命令 kill 旧实例，测试一律用新显示号单命令闭环。
