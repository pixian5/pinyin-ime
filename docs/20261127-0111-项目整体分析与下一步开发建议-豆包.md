# 项目整体分析与下一步开发建议（v0.9.197）

- 日期：2026-11-27 01:11
- 分析基线：`32c0e5b`，`VERSION=0.9.197`
- 分析方式：源码与文档静态审查、Ubuntu 24.04 chroot 真实评测、GitHub Actions 实跑记录、仓库数据/许可证核查、逐键延迟实测
- 本文只列问题与可执行建议，不写成绩。

## 0. 结论摘要

1. **当前对外准确率 42.67% 不能作为真实水平**。1200 句 holdout 的原文 100% 出现在 `bench/corpus`，而字符 trigram 模型正是用 `bench/corpus` 训练的；这是训练集泄漏，不是重排序泛化能力。
2. **去掉逐句原文重叠后，字符模型没有正收益**。用同一版本 CLI、同一 holdout，去掉与 holdout 完全相同的训练句后重训字符模型，结果为 **26.50% 句级 / 85.62% 字级**；不启用字符重排为 **27.83% / 84.81%**。即 alpha=2.0 的字符模型在当前数据分布下反而拉低 1.33pp 句级。
3. **候选召回上限被低估**。`nbest=10` 的 recall@10 是 46.08%，但 addon 默认 `NBest=45`，实测 recall@45 为 **53.58% 句级 / 92.23% 字级上限**。把 46.08% 当成“硬上限”会误判路线。
4. **双前端仍然分叉**。日期时间、网络热词、快捷回复、长句预设、输入统计、剪贴板等能力主要只在 CLI；fcitx5 addon 实际可用的功能少于 README 给人的印象。
5. **公开发布有数据许可风险**。仓库公开包含 LCCC 研究用途语料、人民网新闻、百度百科摘要、中文维基文本，以及由这些语料训练的字符模型；LCCC 在 README 里已注明“分发需另评估”，但 `bench/corpus/lccc_eval.txt` 仍在仓库里。
6. **工程门禁现在能跑，但守的是错误基线**。GitHub Actions 已真实跑通 `ci_static.sh + ci_build.sh`，但 `bench/baseline.json` 前移到 42.67% 后，任何诚实的无泄漏模型都会被判“退步”。

因此下一步不应继续堆功能或调 alpha，而应按下面顺序走：**先修评测可信度 → 再清数据许可 → 再统一双前端 → 最后才做 LM/重排序冲刺**。

## 1. 准确率与评测：先证伪 42.67%

### 1.1 复现结果

同一 commit、同一 CLI、同一 1200 句 holdout，只替换字符模型：

| 配置 | 句级首选 | 字级准确率 | 说明 |
|---|---:|---:|---|
| 训练语料含 holdout 原文（当前 `data/char_trigram.bin`） | **42.67%** | **88.88%** | 与 README/基线一致，可复现 |
| 去掉与 holdout 完全相同的训练句后重训 | **26.50%** | **85.62%** | 仍有同文档/同领域重叠，属偏乐观的初步值 |
| `--no-rerank`（nbest=5 或 10 实测相同） | **27.83%** | **84.81%** | 当前真实引擎基线 |

分域对比（句级 / 字级）：

| 域 | 含泄漏模型 | 去逐句重叠模型 | 无重排 |
|---|---:|---:|---:|
| baike | 43.00 / 90.62 | 28.33 / 88.23 | 26.00 / 86.80 |
| news | 50.67 / 91.74 | 32.00 / 88.38 | 35.00 / 88.11 |
| recent | 47.33 / 90.62 | 28.67 / 86.71 | 34.33 / 87.22 |
| wiki | 29.67 / 82.55 | 17.00 / 79.15 | 16.00 / 77.11 |
| **合计** | **42.67 / 88.88** | **26.50 / 85.62** | **27.83 / 84.81** |

### 1.2 泄漏证据链

- `bench/make_holdout.py` 从 `bench/corpus/{news,wiki,baike,recent}.txt` 抽句；脚本自己的 caveat 写明“未对 LM 训练语料做去重，只能用于版本间回归对比，不能对外宣称绝对准确率”。
- 实测 1200 句 holdout 的期望文本 **1200/1200 全部**能在 `bench/corpus` 中找到原文。
- `scripts/train_char_lm.py` 默认读取 `bench/corpus` 下全部 `*.txt`，包括 `lccc_eval.txt`；模型见过 holdout 的完整字符序列。
- `bench/check_leakage.py` 只检查预设、模板、旧评测语料，**没有检查训练语料/模型**，所以 CI 一直“零泄漏通过”。
- `cpp/char_lm.h` 注释称 alpha=2.0 来自 holdout dev/test 对半调参；但模型本身已经见过整个 holdout，调参口径同样被污染。

结论：42.67% 的本质是“字符 trigram 在候选里认出了训练时见过的原句”，不是“更会选候选”。它接近 recall@10 的 46.08%，恰好说明增益来自记忆上限，而不是泛化。

### 1.3 召回上限不是 46.08%

用 `libime_bench` dump 45 个候选，`bench/recall.py` 统计：

| nbest | recall@1 | recall@5 | recall@10 | recall@20 | recall@45 | 字级上限 |
|---|---:|---:|---:|---:|---:|---:|
| 10 | 27.83% | 41.42% | 46.08% | — | — | 90.21% |
| 45 | 27.83% | 41.42% | 46.08% | 49.58% | **53.58%** | **92.23%** |

addon 默认 `NBest=45`，`rerankPool()` 也取 45；所以 addon 的真实句级上限是 53.58%，不是 46.08%。CLI 为了评测/启动成本只解码 10 个，二者口径不同。

### 1.4 延迟不是当前瓶颈

对 200 条新闻句、12,380 个有效键做逐键实测（chroot，Release）：

| nbest | 平均 | P50 | P90 | P99 | 最大 |
|---|---:|---:|---:|---:|---:|
| 10 | 0.89ms | 0.75ms | 1.62ms | 2.23ms | 4.94ms |
| 45 | 1.30ms | 1.20ms | 2.25ms | 3.43ms | 7.61ms |

nbest 45 的 P99 仍低于 4ms，说明“扩池到 45”在延迟上可行；真正的问题是重排序模型是否泛化，而不是池子大小。

### 1.5 句长分层说明“整句首选”本身很苛刻

无泄漏模型与无重排按 gold 长度分层：

| gold 长度 | 句数 | 无重排句级/字级 | 去重叠字符模型句级/字级 |
|---|---:|---:|---:|
| 0–9 | 104 | 46.2 / 79.5 | 41.3 / 79.5 |
| 10–19 | 429 | 32.6 / 84.0 | 33.3 / 85.1 |
| 20–29 | 547 | 22.3 / 86.0 | 20.5 / 86.6 |
| 30–39 | 112 | 20.5 / 87.5 | 17.9 / 88.9 |
| 40–49 | 8 | 12.5 / 79.7 | 0.0 / 79.1 |

这说明：
- 长句“整句一次全对”本来就会快速下降，不能把它等同于用户体感；
- 字符模型在中短句上明显伤害首选，长句只略微改善字级；
- 需要补“词/短语首选、上屏所需按键数、翻页次数”这类用户指标，不能只看整句 exact match。

## 2. 产品与架构：CLI 与 fcitx5 不是同一条产品线

### 2.1 功能分叉

代码事实：

- `cpp/pinyin_ime_cli.cpp` 多次调用 `boost_v11()`、`quick_candidates_v11()`、日期/计算器/热词/快捷回复/长句模板。
- `fcitx5-addon/pinyinime.cpp` 只调用了 `lookup_suffix_boost_index()` 和 `is_calculator_input()/calculator_eval()`；没有调用 `boost_v11()` 或 `quick_candidates_v11()`。
- addon 虽然 `#include "quick_input.h"`，但大部分 v11 功能没有接线，属于“编译进来但用户用不到”的代码。

实际能力矩阵应按下面口径写，而不是把 CLI 功能当成输入法功能：

| 能力 | CLI | fcitx5 addon |
|---|---|---|
| 全拼 / 简拼 / 双拼 / 模糊音 | 有 | 有（模糊音默认关闭） |
| 整句候选 / 用户学习 / 表情 / 撤回 / 标点 | 有 | 有 |
| 计算器 | 有 | 有（单独调用） |
| 日期时间、网络热词、快捷回复、长句预设 | 有 | **没有** |
| 输入统计、剪贴板、i/u 模式、Tab 补全 | 有 | **没有** |
| 云拼音 | CLI 有 | addon 有，但默认关闭、只验证过 mock |
| 配置 UI | 配置文件 | fcitx5 配置页（部分项） |

这不是“功能多”，而是“功能在错误的入口上”。真实用户用 fcitx5，CLI 主要是测试/脚本入口；继续往 CLI 堆功能，产品收益接近于零。

### 2.2 代码结构

- `cpp/pinyin_ime_cli.cpp` 3,602 行，`fcitx5-addon/pinyinime.cpp` 1,878 行；候选 boost、英文判定、标点、撤回、日期/计算器、纠错等逻辑仍有重复。
- `cpp/quick_input.h` 已拆成 umbrella + 10 个片段头，但 `quick_input_boost.h` 1,674 行、`quick_input_stats.h` 969 行、`abbr_presets.h` 982 行，仍是“第二套引擎”。
- `cpp/correction_data.h` 188,950 行 / 2.0MB，直接编译进二进制；应改为生成 `.cpp` 或运行期数据，降低编译时间与头文件耦合。
- `fcitx5-addon/wayland_integration.h` 只被测试引用，产品代码未使用；要么接线，要么删除。

### 2.3 默认配置与数据路径

- `fcitx5-addon/pinyinime.h` 的 `DataDir` 默认值是 `/root/.local/pinyin-ime/share/libime`，对普通用户是错误路径。虽然代码会回退到 `/usr/share/libime`，但配置页会把错误默认值暴露给用户。
- 云拼音每次前缀输入都可能发请求，代码没有 250ms 防抖；只在 mock 上验证过，真实服务端未对接。
- `CloudEndpoint` 允许 `http://`，API key 明文存配置；如果要公开发布，需要 TLS 强制、防抖、隐私说明。

## 3. 数据、许可证与发布风险

这是比“准确率少几个点”更优先的发布阻断项。

### 3.1 公开仓库包含受限语料

当前 GitHub 仓库是 public，`git ls-files` 里仍有：

- `bench/corpus/lccc_eval.txt`：来自 LCCC。README 明确写“许可为 LCCC 自定义（研究用途），分发需另评估”；但这份文件已入库，且被 `train_char_lm.py` 用于训练。
- `bench/corpus/news.txt`：人民网 RSS 新闻正文。
- `bench/corpus/baike.txt`：百度百科词条摘要。
- `bench/corpus/wiki.txt`：中文维基文本；CC BY-SA 需要署名/相同方式共享，仓库没有单独的数据许可与 attribution。
- `data/char_trigram.bin`：由上述语料训练出的模型，属于衍生分发，不能只按代码的 LGPL 处理。
- `data/user_lm_news/user.history`：二进制用户历史文件入库；无论内容是测试数据还是真实输入，都不应出现在公开仓库。

### 3.2 发布建议

- 在数据许可理清前，把仓库改为 **private**，或至少先把 `bench/corpus/`、`bench/holdout/`、`data/user_lm_news/` 移出公开跟踪。
- 原始语料改为 `fetch_*` 脚本按需下载，仓库只保留 SHA256、抽样小样本和许可说明；不要把抓取正文当源码分发。
- 建立 `docs/DATASETS.md`：逐项写来源、许可、是否可再分发、是否可用于训练、模型是否衍生。
- 字符模型重新用可再分发的语料训练；如果暂时做不到，发布包不要带模型，或只在国内/私有环境使用。
- `data/user_*`、`user.history`、`user.lm` 加入 `.gitignore`，并提供清理脚本。

### 3.3 发布工程

- `packaging/debian/control`、`packaging/pinyin-ime.spec`、`scripts/make_deb.py` 里仍有 GitCode 邮箱/Homepage；迁到 GitHub 后没有同步。
- `.gitlab-ci.yml` 仍引用 `gitcode.com/fcitx/libime.git`，但项目已经迁到 GitHub；这是死流水线，应删除或标注归档。
- GitHub Actions 只有 `build-eval` 一个 job：不跑安装矩阵、不跑真实 fcitx5、不产出 deb/rpm/release、不做 ARM64。
- `bench/baseline.json` 的 42.67% 会让 CI 持续为泄漏模型背书。

## 4. 测试与文档

- 单测 721 条、覆盖率 92.7% 是有效资产，但主要集中在 `quick_input` / 纠错 / 云拼音；addon 的按键状态机没有独立单测。
- `ci_build.sh` 已包含编译、单测、警告、快照、fuzz、评测，是当前最可信的本地门禁；但它默认加载 `data/char_trigram.bin`，所以门禁本身被泄漏模型污染。
- `README.md` 8,559 行，仍有多个历史“当前版本”标题；根目录 `PROJECT_STATUS.md` 还写 v0.9.196 / v0.9.121 发布状态，`PROJECT_RULES.md` 还写 0.9.176，`ARCHITECTURE.md` 仍描述 Web Demo/Daemon/Post-Corrector 与当前主链路不完全一致。
- `文档索引.md` 只覆盖 `docs/`，根目录 `ANALYSIS.md`、`PLAN-A.md`、`RESULTS.md`、`USABILITY_REPORT.md` 等没有索引；新接手的人无法判断哪些是历史、哪些是现行。

## 5. 下一步路线图

### P0：先让指标可信（建议 3–5 个工作日，期间冻结功能）

#### P0-1 建立文档级 train/dev/test 切分

- 新增 `bench/split_corpus.py`：按文章来源/URL/条目 ID 分组，**不能按句子随机切**；同一篇文章的句子只能落在同一 split。
- 现有 `fetch_*.py` 输出只保留句子，丢失了文档边界；需要改成 JSONL（`doc_id, url, title, text`），再从 JSONL 生成纯文本。
- 产物：`bench/splits/train.tsv`、`dev.tsv`、`test.tsv`、`manifest.json`（含每个 split 的 sha256、doc_id 列表、字符数）。
- 冻结 test；调参只看 dev；最终只在 test 上跑一次。

#### P0-2 重训字符模型并重新调 alpha

- `scripts/train_char_lm.py` 只读 `train` split；模型头增加元数据：训练语料 sha256、split 版本、alpha、训练日期。
- 在 dev 上扫 `alpha ∈ {0.25, 0.5, 1.0, 1.5, 2.0, 3.0}`，同时记录句级/字级/P50/P99。
- 启用门槛：dev 句级至少 +0.5pp，且字级不下降，且 test 复现；否则默认 `--no-rerank`，不要把模型放进发布包。
- 以当前结果看，alpha=2.0 很可能应被淘汰；不要因为“模型已经做了”就强行保留。

#### P0-3 把泄漏检查扩展到训练侧

- `bench/check_leakage.py` 增加：
  - test 句子与 train 句子 exact match；
  - test 与 train 的字符 5-gram 重叠率（按句子统计，超过阈值即报）；
  - test 拼音串与 train 拼音串重复；
  - 模型元数据里的 train sha256 必须与当前 split 一致。
- CI 先跑泄漏检查，再跑评测；泄漏检查失败直接红，不允许“先评测后解释”。

#### P0-4 重置基线并纠正文档

- `bench/baseline.json` 改为无泄漏 test 的结果；把 42.67% 降级为“历史泄漏复现值”，不再作为门禁。
- README 顶部增加“准确率口径更正”，把 `20261126-2349-字符trigram重排序上线-豆包.md` 标注为“含训练集泄漏，数字不可对外使用”。
- 所有对外数字加三行上下文：语料、split、是否启用字符模型、nbest。

**P0 验收**：从干净 clone 执行一条命令，能重训模型、跑泄漏检查、跑 test、输出可复现报告；`git grep 42.67` 只出现在历史说明里，不再出现在门禁/对外摘要里。

### P0：数据许可与仓库边界（建议 2–3 个工作日，可与 P0-1 并行）

- 先做 `docs/DATASETS.md` 和 `git ls-files` 清单，逐项标注可再分发/仅研究/禁止分发。
- 把 LCCC、人民网、百度百科、维基原文移出公开跟踪；保留抓取脚本、URL、SHA256 和小样本。
- `data/user_lm_news/user.history` 立即 `git rm --cached`，并把 `data/user_*`、`*.history`、`*.lm` 加入 `.gitignore`。
- 字符模型重训前，发布包先不带模型；或者暂时只发 CLI、不发 addon 模型。
- 公开仓库先转 private，直到 `docs/DATASETS.md` 通过自查。

**验收**：`git ls-files` 中不再有受限语料；`docs/DATASETS.md` 能回答“这份数据从哪来、能不能再分发、模型能不能发布”；发布包不包含来源不明的模型。

### P1：统一双前端（建议 1–2 周）

- 抽 `pinyinime_core` 静态库：
  - `EngineSession`：libime 初始化、nbest、词典、用户模型；
  - `CandidatePipeline`：完整候选收集、短候选过滤、boost、字符重排、用户频率、显示索引映射；
  - `InputState`：preedit、光标、分页、撤回、英文/标点状态。
- CLI 与 addon 都只做适配层；删除重复的 boost/英文判定/标点/撤回实现。
- 把 v11 功能按“产品需要”分批复用到 addon：日期/计算器/常用快捷回复优先；网络热词、长句预设、输入统计、剪贴板要么移植，要么从 README 功能表中标成 CLI-only。
- 增加 golden trace：同一串输入在 CLI 与 addon 的候选序列必须逐项一致；addon 状态机可在无 GUI 的 headless harness 中测试。

**验收**：同一份 200 条输入 trace，CLI 与 addon 的 top1/top5 完全一致；addon 单测覆盖分页、选词、撤回、云候选索引；README 功能表有 CLI/addon 两列。

### P1：建立用户指标，不再只看整句

- 新增 `bench/eval_user.py`：
  - 2–6 字词/短语 top1、top5；
  - 整句 exact、字级；
  - 交互模拟：首选对则一次空格；首选错则翻页/选词，统计“上屏所需按键数、翻页次数、选择次数”；
  - P50/P95/P99 每键延迟、首候选出现延迟；
  - 按域、按句长、按简拼/全拼/混输分层。
- 用 5–10 个真实用户、每人 20 条常用句做小样本；只记录匿名候选选择，不记录正文。
- CI 门槛从“整句掉 1pp”改成“用户指标不掉”：词级 top1 掉 >1pp、平均按键数增加 >5%、P99 增加 >2ms 任一即红。

**验收**：能回答“这次改动让用户少按几次键/少翻几页”，而不是只回答“整句 exact 涨了 0.3pp”。

### P1：重排序与 LM，按收益排序

1. **先做轻量 listwise 重排**：用 `nbest_dump` 导出 45 个候选的特征（libime score、字符 LM、词数、用户频率、词典词频、候选长度、是否整句覆盖），在 dev 上训练 logistic regression / LambdaMART。比单独 alpha 更稳，也便于解释。
2. **再做 LM**：用可再分发的混合语料训练更大的 KenLM（4/5-gram）或领域混合 LM，先看 recall@45 是否从 53.58% 提升，再看 top1。不要直接冲 68%。
3. **最后才考虑神经网络重排**：小模型只做候选重排，不做解码；必须有 CPU 延迟预算和离线回退。

**验收**：在无泄漏 test 上，句级至少 +2pp 或字级 +1pp，P99 不增加超过 5ms；否则回滚。目标建议分三层：当前 27.83/84.81 → 近期 32–35/87–89 → 中期 40+/90+；68%/91% 不应作为当前版本承诺。
