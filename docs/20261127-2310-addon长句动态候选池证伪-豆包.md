# addon 长句动态候选池：三轮实验均证伪

## 目标

v0.9.211 的 CLI 长句动态池已验证：`>=54` 个拼音字母时把重排池从 10 扩到 60，默认 1200 句 Top1 377→383（+6 句）。本轮想把这个收益搬到 fcitx5 addon 真实上屏链路：长句用 NBest=60，短输入保持 45。

## 实验一：逐键 setNBest（失败）

做法：每次字母送入 `PinyinContext::type()` 前，按 `rawInput_ + 当前键` 的长度调用 `PinyinIME::setNBest(45/60)`。

结果（每域 20 句）：

| 域 | 基线 Top1 | 逐键 setNBest Top1 | 基线候选池均值 | 实验候选池均值 |
|---|---:|---:|---:|---:|
| baike | 40.0% | 20.0% | 20.0 | 15.2 |
| news | 55.0% | 25.0% | 20.0 | 17.1 |
| recent | 40.0% | 15.0% | 20.0 | 18.1 |
| wiki | 15.0% | 5.0% | 20.0 | 17.1 |

结论：组合过程中调用 `setNBest` 会让 libime 的增量切分/候选状态失效，候选池反而缩水，整句字级从 87% 掉到 38%～43%。这不是阈值问题，而是不能在已有 `PinyinContext` 上中途改 NBest。

## 实验二：只改重排池，不改 NBest（无收益）

做法：`rerankPool()` 按预编辑长度返回 `max(10, 60)`，但 libime 仍只产出 45 个候选。

结果：每域 20 句与基线逐句完全一致（baike 40/87.26、news 55/92.67、recent 35～40/85、wiki 15/81.35）。`full.size()` 仍为 45，扩池是空操作。

## 实验三：跨阈值清空重放（失败）

做法：长度首次达到 54 时，先 `setNBest(60)`，再 `ctx.clear()` 并用整串重放；之后不再改 NBest。这样避开「中途改 NBest」对已有上下文的破坏，理论上等价于 CLI 的整串解码。

结果：

- 普通 20 句子集：与基线逐句一致，无回归也无提升。
- 120 句长句专集（每域 30 条最长句）：与基线逐句完全一致。
- baike 全量 300 句：**30.67% / 89.23%**，低于 v0.9.210/v0.9.211 的 baike **31.0%**；Top5 46.33%、Top10 51.33%、MRR 0.3777。

结论：长句重放没有带来 CLI 的 +6 收益，反而在 baike 掉 0.33pp。CLI 的长句收益依赖整串一次性解码；addon 逐键语境下即使重放，也已丢失前缀阶段形成的切分状态，无法等价复现。

## 离线参数复核

用 `tmp/nbest45_dump.tsv` 的 54,000 条候选复算 addon 现有公式 `base + 0.25*charLM`，门限 `base < maxBase - 1.0` 时 `-1`：

- 门限扫描 0.6 / 0.8 / 1.0 / 1.2 / 1.5 / 2.0 / 3.0：Top1 为 30.17 / 30.42 / **30.67** / 30.67 / 30.42 / 30.33 / 30.33，1.0～1.2 已是最优。
- alpha 扫描 0.05～1.0：0.25 最优（30.67），0.20 为 30.58，0.30 降到 30.25。
- 门限长度 0～30：18 字最优（30.67）；0～16 为 30.58。
- 额外长度/词数先验全部无收益；排名先验 -0.005 仅 +1 句，属于噪声级。

## 结论

- 不改 addon 候选池，保持 v0.9.211 的 NBest=45、重排池 10、门限 1.0、alpha 0.25。
- 本轮源码已回滚，`VERSION` 仍为 `0.9.211`，不发布 v0.9.212。
- 后续 addon Top1 不应继续在「候选池大小 / 线性先验」上打转；优先考虑独立上下文重排、词级语言模型二次打分，或从 wiki 低分域做误差分析。
