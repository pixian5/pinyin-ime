## 关键经验（踩坑记录，后续复现必读）

1. **fcitx5-gtk 是纯客户端库，用系统 gcc 编译**：它自带 `Fcitx5GClient`，经 DBus 与 fcitx5 守护进程通信，不链接 fcitx5 核心库 → 与 fcitx5 二进制无 ABI 耦合。若用 conda-gcc 编译，im module 会带 conda 的 libstdc++ 依赖，加载进系统 GTK3 应用时可能符号版本冲突；用系统 gcc 10.3 最稳。
2. **openEuler GTK3 的 immodule 发现机制是「immodules.cache 缓存文件」，不是运行时扫描**：strace 实测 GTK3 只 open `/usr/lib64/gtk-3.0/3.0.0/immodules.cache`，不扫目录、也不读 `GTK_PATH`。必须用 `gtk-query-immodules-3.0-64`（openEuler 的 multiarch 命名，非 `gtk-query-immodules-3.0`）生成缓存写入系统路径（需 root）。缺缓存 → `GTK_IM_MODULE=fcitx` 被静默忽略、退回 simple 透传。
3. **fcitx5 冷启动后是「未激活」态，必须先 Ctrl+Space 激活输入法**：否则按键全部透传为裸拉丁字符（`GTK_COMMIT:n GTK_COMMIT:i ...`）。XIM 测试每个用例都以 `\S`（Ctrl+Space）开头正是这个原因。gtk 端到端同理。
4. **dbus-daemon 地址解析**：`dbus-daemon --session --fork --print-address=1` 在未设 `XDG_RUNTIME_DIR` 时会先往 stderr 打一条「transient service directory ... not available」警告，混进合并输出里；解析地址要 `grep '^unix:'` 而不是 `head -1`。
5. **`pkill -f "dbus-daemon --session"` 会误杀自己的 shell**：`-f` 按完整命令行匹配，运行该命令的 `bash -c` 进程自身命令行里也含这个字符串。杀 daemon 用 pid 文件或 `pkill -x dbus-daemon`（按进程名精确匹配）。
6. **GTK3 im module 的 dbus 对象路径**：fcitx5-gtk 与守护进程通信用的是总线名 `org.fcitx.Fcitx5` + 对象路径 `/org/freedesktop/portal/inputmethod`（`org.fcitx.Fcitx.InputMethod1` 接口，路径名容易误以为是 XDG portal，实为 fcitx5 自身协议约定），与 xdg-desktop-portal 无关，不需要 portal 进程。
