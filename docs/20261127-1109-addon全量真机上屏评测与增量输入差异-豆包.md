# addon 全量真机上屏评测与增量输入差异（v0.9.202）

## 结论

- 新增 `scripts/eval_addon_batch.py` / `.sh` 后，在私有 Xvfb + dbus + fcitx5 5.1.7 + GTK3 环境里跑完 1200 句 clean holdout：addon 真实上屏 **句级 28.00% / 字级 80.31%**，864 句不是首选整句。
- 这个数字**不能直接和 CLI batch 的 30.00% / 86.04% 比较**。CLI `--batch` 是“整串拼音一次性解码”，真实 fcitx5 是“每个按键刷新候选”；同一句长 baike，CLI batch 首选“文献多见”，而 CLI 交互模式和 addon 都首选“文戏安多”。addon 反映的是用户真实路径，不是采集时序 bug。
- 因此 addon 28.00% / 80.31% 应作为**真实输入基线**；CLI batch 30.00% / 86.04% 只能当“一次性解码上限/回归基线”。下一步要先补 CLI 逐键交互评测，再谈 addon 与 CLI 的差距。

## 评测方法

```bash
bash scripts/eval_addon_batch.sh --out /tmp/addon-eval-full
```

脚本启动独立 Xvfb、`dbus-run-session`、`fcitx5` 和最小 GTK3 Entry；`xdotool` 逐句敲 holdout 拼音，空格提交，轮询 Entry 直到读到非空文本。每句前 `CLEAR`，窗口 focus 后等 0.8s，空格后最多等 1.2s。调试时保留现场用：

```bash
PINYINIME_EVAL_KEEP=1 bash scripts/eval_addon_batch.sh --limit 1
```

## 关键证据：batch 与逐键输入不是同一路径

输入：

`gaicizuizaojianyusanguozhimingdaiwenxianduojianqushiyouliyongfaqingdaizhanggaowenlunjiqushizhishu`

- CLI `--batch --top1`（nbest=10/45）：`该词最早见于三国志明代文献多见去世有利用法清代长高文论及趋势指数`
- CLI 交互模式逐字敲同一串，首个候选：`该词最早见于三国志明代文戏安多减去是由利用法清代长高文论就爱趋势指数`
- addon 真实上屏：`该词最早见于三国志明代文戏安多渐趋是由利用发情呆帐高温论及趋势指数`（字级 60.61%）

三者的差异来自 libime 在“整串解码”与“每键刷新”两种用法下的切分不同，不是 addon 的 `displayToRaw_` 索引错位，也不是 xdotool 丢键：addon 的 preedit 紧凑串与输入 97 个字母完全一致。

## 延迟口径

表中的 P50/P95/P99 是**整句墙钟时间**，包含 `xdotool` 逐键 5ms、敲完后的 100ms settle、空格提交和轮询；不是 addon 引擎单次转换耗时。短句 P50 约 500ms 主要来自按键注入，不能当作输入法卡顿。长句 P95 超过 1.7s，除了按键数，还包含增量解码和提交等待，需要单独拆成 `type_ms` / `commit_ms` 再评估。

## 风险与下一步

1. 给 CLI 增加 `--incremental`（逐字符 `ctx.type` 并每键取候选），产出与 addon 同路径的基线；不要再用 batch 数字评价真实输入。
2. 在 addon 提交路径做实验：长输入（如 compact ≥ 24）在空格时用完整 raw input 重建一次 context，再做字符重排选首选；同时保证候选窗在提交前同步，避免“看到的首选和上屏的不一致”。
3. 长句 UI 刷新降频：候选列表和字符重排不必每键全量跑，可在 50–100ms 去抖；当前长句 P95 仍有 1.7s，用户能感知。
4. addon 评测补 Top-k/MRR/翻页成本，当前只有 top1 和字级；否则无法判断“首选差一点”还是“候选埋太深”。
5. 把 1200 句 addon 全量评测放手动/夜间 job；每次 push 仍只跑 8 句 `addon-acceptance`，避免 CI 变慢。
6. 数据许可和 public 仓库语料问题仍未解决；全量评测脚本本身不改变许可状态。
