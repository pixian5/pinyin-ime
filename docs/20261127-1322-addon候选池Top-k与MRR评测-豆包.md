# addon 候选池 Top-k 与 MRR 评测（v0.9.204）

## 结论

addon 真实上屏的瓶颈不只是“候选池里没有正确句”，而是“正确句在池里但没排到首位”。

1200 句 clean holdout，addon 空格上屏：

| 口径 | 结果 |
|---|---|
| Top1 句级 | 30.25% |
| Top5 句级 | 45.17% |
| Top10 句级 | 49.83% |
| MRR | 0.3689 |
| 字级 | 86.24% |

Top5 比 Top1 高 **14.92pp**，Top10 再高 4.66pp。也就是说，约 15% 的句子正确答案已经在用户翻 1 页内，但首选排序错了。下一阶段的主线应从“扩召回”转向“重排”，尤其是 wiki（Top1 18.67%、Top10 37.00%、MRR 0.2482）。

## 实现

- `fcitx5-addon/pinyinime.cpp` 新增评测专用候选转储：仅当 `PINYINIME_EVAL_CAND` 环境变量存在时，在空格提交前把当前候选按**实际显示顺序**写入 TSV；正常用户路径零 I/O。
- 必须按显示顺序导出：`displayToRaw_` 重排、`boostSwap_`、`boostInsertWord_`、云候选都会改变空格实际选中的候选；直接倒 libime 原始列表会出现 Top1 与上屏结果不一致（实测 4 句里 2 句不一致）。
- 每次最多导出 20 条，覆盖 Top1/5/10；`scripts/eval_addon_batch.py` 读取后计算 `top1/top5/top10_sent_acc`、`mrr`、`candidate_pool_avg`，并写入 `summary.json` 与 `report.md`。
- Top1 与原有 `sent_acc` 对齐（4 句功能集均为 75.0%），证明转储顺序与 `selectCandidate(0)` 一致。

## 补充：简单重排权重扫描

在 CLI nbest45 上扫 `CharLM::kAlpha`（不改 addon 编译）：

| alpha | Top1 | 字级 |
|---|---|---|
| 0.25（当前） | 30.33% | 86.24% |
| 0.50 | 29.42% | 86.13% |
| 1.00 | 26.67% | 85.75% |
| 1.50 | 25.33% | 85.54% |

当前 0.25 已是最优，继续加大字符 LM 权重只会把候选排得更差。离线试了候选词数/长度线性惩罚：`score + 0.25*char + 0.1*wordCount` 只到 30.42%（+0.09pp），不足以抵消代码复杂度，不落地。下一步需要学习型重排或更强的词级 LM，不是再调一个标量。

## 已撤销的实验

尝试在空格提交前对 5–8 字母非全拼缩写补一次 `disambiguate_if_needed`，想让 `xianyoud` 恢复。实测：
- `xianyoud` 仍输出“西安有点”，没有变成期望的“闲游的”；
- 全量准确率仍为 30.25/86.24，没有提升；
- P50 从 489.7ms 升到 505.1ms，P95 从 599.1ms 升到 647.9ms。

该改动已撤回，不进入 v0.9.204。`xianyoud` 属歧义缩写，靠消歧无法稳定产出“闲游的”，需要专用 boost 或词库，暂不处理。
